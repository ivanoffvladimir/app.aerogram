# Состояние работ

> **30 августа 2026: пришло ТЗ v3, продукт переопределён.**
> Центром стал Decision Engine, перевозчиков пять вместо одного, деньги переходят
> в минорные единицы, фронт — на Next.js. Решение по итогам разбора: **переделываем
> этот репозиторий, а не начинаем новый** — сохраняется около двух третей бэкенда.
> Разбор расхождений и план — раздел «Переход на ТЗ v3» ниже.
> Всё, что описано в разделе «Готово», написано по ТЗ v1 (`docs/tz/archive-v1/`)
> и читать его нужно с этой поправкой.

Обновляется по завершении каждого этапа плана.

### Ревью миграций (требование CLAUDE.md §7)

Построчное ревью схемы нашло три дефекта, все исправлены:

* **Замороженные значения по умолчанию.** В миграции 0001 восемь колонок
  времени получили `server_default`, заданный питоновской строкой `"now()"`
  вместо `sa.text("now()")`. PostgreSQL вычислил его один раз при миграции,
  и `DEFAULT` стал литералом с моментом выполнения. Доказано: две записи
  в `audit_log` с разницей в секунду получили одинаковый штамп. Аудит-лог
  (12.6 ТЗ) переставал быть доказательством. Починено миграцией 0005,
  всем колонкам добавлено питоновское значение по умолчанию, регрессия
  закрыта тестом.
* **Мёртвый индекс** `ix_counterparties_tenant_id_inn`: планировщик не
  выбирает его никогда, точное сравнение обслуживает индекс по префиксу ИНН.
  Удалён.
* **Дубль индекса**, созданный мной же в 0004: `ix_counterparties_tenant_id_name`
  полностью перекрывается частичным `ix_counterparties_tenant_id_alive`.
  Удалён старый.

Дополнительно: все индексы, включая частичные и по выражениям, объявлены
в моделях — иначе автогенерация следующей миграции предложила бы их удалить.
После этого `alembic check` перестал шуметь и добавлен в CI вместе
с проверкой «голова миграций одна».

### Неделя 5 — расчёт по API СДЭК

* Клиент СДЭК: OAuth `client_credentials`, кэш токена в памяти процесса
  с запасом перед истечением, однократная переавторизация при отзыве токена,
  защита от параллельных авторизаций одной учётной записью.
* `quote`: расчёт по доступным тарифам, нормализация тарифов, фильтрация
  выдачи по режиму доставки, разбор ошибок перевозчика в доменные.
* `fetch_refs`: выгрузка городов СДЭК с их кодами.
* Rate shopping (`POST /api/v1/rates`): параллельный опрос учётных записей
  тенанта, таймаут на перевозчика и общий дедлайн (FR-1.3), неответившие —
  отдельными строками выдачи (FR-1.4), сохранение запроса и котировок
  вместе с сырьём (FR-1.7), комбинированный ранг (FR-5.3, FR-5.4).
* Контракт СДЭК сверен с исходниками официального SDK (ADR-0010).

Две ошибки, найденные тестом уже по написанному коду:

* нечитаемые учётные данные ОДНОГО перевозчика роняли весь расчёт: расшифровка
  бросает `InvalidTag` из cryptography, а перехватывался только `ValueError`.
  Это прямое нарушение FR-1.4 — ошибка одного перевозчика не должна ронять
  выдачу;
* список задач опроса фильтровался, а индекс для строки таймаута брался
  из нефильтрованного списка: при пропуске одной учётной записи строка
  «не ответил» назвала бы чужого перевозчика.

## Переход на ТЗ v3

### Что сохраняется

| Модуль | Строк | Судьба |
|---|---:|---|
| `carriers/` — контракт, HTTP-слой, реестр, карты статусов | 1026 | Сохраняется: ТЗ v3 §9 требует те же методы плюс `health_check` |
| `core/` — тенанты, RBAC, JWT, аудит, шифрование | 1376 | Сохраняется: §2 требует ровно это |
| `directories/` — лестница ФИАС, city_carrier_map | 1636 | Сохраняется: §7 требует mapping-таблицу городов |
| `shared/` | 714 | Сохраняется, кроме модуля денег |
| `rating/` | 624 | Механика fan-out сохраняется, DTO и ранжирование переписываются |
| Тесты | 3636 | Сохраняются |
| `frontend/` | 519 | Выбрасывается: ТЗ требует Next.js |

Изоляция тенантов у нас **строже требований**: ТЗ v3 просит проверять tenant scope
в service/repository, у нас RLS на уровне PostgreSQL и роль без `BYPASSRLS`.
Не переделываем, оставляем как есть.

### Что ломается

1. **Деньги.** `NUMERIC(12,2)`/`Decimal` → `BIGINT amount_minor` + `CHAR(3) currency`
   (backend ТЗ §4, схема `Money` в OpenAPI, фронт §10). ADR-0011.
2. **Нет ядра нового продукта.** `Recommendation`, `Decision`, `DeliveryOutcome`,
   `CostComponent`, `RoutingRule` — достройка модулей `routing/`, `intelligence/`,
   `billing/`, а не переделка существующих.
3. **Major Express первым, SOAP/WSDL.** Новая зависимость `zeep`, ADR-0013.
4. **Контракт API** переписывается под `docs/tz/v3/openapi.yaml`: пути `/v1/*`,
   плоский `address_line` вместо `city_fias_id`, `weight_grams`/`length_mm`.
5. **Фронт** на Next.js, ADR-0012.

### Ревью безопасности

Отдельный проход по аутентификации, RLS, криптографии и инъекциям. Четыре
находки прошли независимую проверку на ложное срабатывание; две отсеялись
(область действия API-ключей и приостановка тенанта — невстроенные функции,
а не обход существующего контроля). Две подтверждены и закрыты:

* **Обход второго фактора.** Принималась любая строка из шести символов.
  Вход с `mfa_enabled = true` теперь закрыт наглухо до появления верификатора —
  см. пункт 0 раздела «Требует решения человека».
* **Подъём привилегий через границу тенанта.** `UserCreate.role` принимал
  полный `UserRole`, включая `platform_admin`, а `POST /v1/users` открыт
  владельцу любого тенанта. Владелец мог выдать себе платформенную роль
  и через `/v1/admin/city-mappings/*` испортить `city_carrier_map` —
  таблицу без `tenant_id` и без RLS, которая читается на расчёте у всех
  тенантов сразу. Теперь тело запроса типизировано `TenantRole`, где
  платформенных ролей нет физически, плюс второй барьер в `UserService.create`.

Признано здоровым: покрытие RLS полное на всех 22 таблицах с `tenant_id`;
оба окна `app.auth_scope` только на SELECT, транзакционные, с разными
значениями; инъекций нет; SSRF нет; криптография корректна; обработчики
ошибок не протекают.

Побочная функциональная находка, тоже исправлена: `ApiKeyService.resolve`
вызывала `touch_used` до установки тенанта, поэтому под RLS `UPDATE`
не находил строк и `last_used_at` не записывался никогда. Отметка вынесена
в `mark_used` и вызывается после `set_tenant` — тем же порядком, что и работа
с пользователем в ветке JWT.

### Ревью и прогон тестера

Полный прогон обоих разделов плюс построчное ревью ветки нашли девять
дефектов. Все исправлены и закрыты тестами.

Три ломали продукт в бою:

* **Аутентификация по API-ключу не работала вовсе.** Тенант определяется
  по ключу, значит на момент поиска `app.tenant_id` не установлен, а политика
  `tenant_isolation` на `api_keys` объявлена с `FORCE` и не отдаёт строк.
  Любой запрос с `X-Api-Key` получал «Ключ недействителен». Комментарий
  в репозитории ссылался на класс `ApiKeyAuthService`, которого никогда
  не существовало, и ни один тест этот путь не покрывал. Починено миграцией
  0008 — узкое окно только на SELECT, по образцу входа (ADR-0004).
* **Дедлайн без часового пояса ронял расчёт в 500.** Наивный момент вычитался
  из момента с зоной. Теперь отвергается на границе с указанием, что прислать:
  достроить зону значило бы выбрать её за клиента, а для Москва → Владивосток
  разница в семь часов решает, уложился ли перевозчик.
* **Регион из одних пробелов или точки ронял расчёт в 500**: первое слово
  бралось по индексу из пустого списка.

Три искажали данные, ради которых продукт существует:

* **Повтор решения создавал второе решение.** Ключ идемпотентности создавался
  внутри мутации, то есть заново на каждую попытку. Теперь живёт столько же,
  сколько намерение оператора, и сбрасывается новым расчётом.
* **Предложение без даты обнуляло вес срока в «оптимальном».** Сентинел
  `10**12` растягивал шкалу на века, и разница между реальными сроками
  схлопывалась в ноль.
* **`no_deadline_match` ставился, когда просто никто не ответил.** «Никто
  не успевает» требует показать альтернативы, «никто не ответил» — разобраться
  с доступностью; в снимке они были неразличимы.

Остальные три: клиент по API-ключу не мог зафиксировать решение (нарушал
ограничение схемы и получал невнятный 409 вместо указания прислать
`mode="auto"`); проверка в E2E не ждала ответа и потому никогда не срабатывала;
при переходе на Next.js потерялся `eslint-plugin-react-hooks`, и нарушения
правил хуков перестали ловиться.

Отдельно: E2E переведены с `next dev` на продакшн-сборку. Dev-сервер после
правок файлов уходит в `__webpack_modules__ is not a function`, страница
перестаёт гидрироваться, и тест проверяет не то, что отгружается.

### Сделано в переходе

* Сущности Decision Engine: `rate_offers` с `cost_components`, `recommendations`,
  `decisions`, `delivery_outcomes`, `routing_rules`; RLS на всех пяти новых
  таблицах, миграция `0007_decision_engine`, обратимость проверена.
* Переименование по контракту: `rate_requests` → `rate_quotes` (снимок запроса),
  `rate_quotes` → `rate_offers` (предложение). В ЭРД и OpenAPI «quote» — это
  запрос, а не предложение; расхождение имён кода и контракта пришлось бы держать
  в голове у каждого, кто читает и то и другое.
* Routing Engine: четыре стратегии, факты объяснения, `POST /v1/routing/quote`
  и `POST /v1/decisions` с обязательным `Idempotency-Key`.
* API приведён к `docs/tz/v3/openapi.yaml`; тест соответствия сторожит
  расхождения и ведёт список ещё не реализованных путей.
* Фронт переписан на Next.js (ADR-0012): вход и экран Rate Shopping —
  стратегии, карточка рекомендации с объяснением, расшифровка стоимости,
  диалог override, признаки stale quote и partial failure. Клиент API
  генерируется из `docs/tz/v3/openapi.yaml`.
* Неизменяемость решения — триггером в БД, а не соглашением в коде: приложение
  обходится скриптом, триггер нет.
* Отправления: `POST /v1/shipments` с обязательным `Idempotency-Key`, список
  с фильтрами контракта, карточка, отмена. Миграции не потребовалось — схема
  недели 2 содержала всё нужное.
* **Защита от «призраков» (FR-2.5)** построена на трёх свойствах, и ни одно
  не работает без остальных. Черновик коммитится **своей транзакцией до**
  обращения к перевозчику: транзакция запроса откатилась бы вместе с ним
  ровно тогда, когда запись о намерении нужна больше всего. Отсюда главное
  следствие — если строки нет, то и обращения к ТК не было, и на свежем
  черновике сверять нечего. Номер выводится из ключа идемпотентности и уходит
  перевозчику как номер клиента. Повтор начинается со сверки: адаптер
  спрашивает ТК о заказе с нашим номером, и найденный заказ принимается
  в базу, а не создаётся второй.
  Каждое из трёх свойств проверено тестом, который краснеет без него: без
  отдельной транзакции черновик исчезает вместе с ответом, без сверки повтор
  создаёт у перевозчика второй заказ на тот же груз.
* Отмена черновика тоже идёт через сверку: бросить заказ, о котором мы
  не знаем, — это и есть призрак.
* Трекинг: единая лента событий (`GET /v1/shipments/{id}/tracking`),
  нормализация статусов по YAML-картам, дедупликация по отпечатку события,
  проекция на отправление, `DeliveryOutcome` и адаптивное расписание опроса
  по таблице FR-3.2. Модуль сознательно **не ходит к перевозчикам**: он
  принимает уже полученные события, а опрос делает `shipments`, где адаптер
  и расшифрованные доступы уже есть.
  Два свойства проверены тестом, который краснеет при правдоподобной ошибке —
  сортировке ленты по времени получения вместо времени события: она показала
  бы доставку раньше отправки и откатывала бы статус назад догоняющим старым
  событием. Дедупликация проверена так же: без неё повторное событие роняет
  всю пачку на уникальном индексе.
* Отсутствие карты статусов перевозчика больше не роняет приём событий:
  событие сохраняется с сырым статусом и признаком «не сопоставлено», то есть
  попадает в очередь ручного разбора. Сам загрузчик карт по-прежнему бросает
  исключение — это ошибка настройки, и молчать о ней нельзя.
* `eta` и `deadline` в ответе об отправлении заполняются из снимка расчёта
  пакетным запросом: оператору важно не «когда обещали», а «успеваем ли».
* Carrier Score: формула раздела 10.1 (`intelligence/score.py`), байесовское
  сглаживание с приором 20, пороги доверия FR-7.3, снапшоты с версией формулы
  и `GET /v1/analytics/carriers` с расшифровкой по компонентам (FR-7.5).
  Формула вынесена в отдельный модуль без зависимостей намеренно: это тот код,
  где ошибка не падает, а тихо меняет советы, которые продукт даёт клиенту.
  Холодный старт закрыт так, как требует раздел 10.2: при выборке меньше
  десяти скор не считается вовсе — наружу уходит «недостаточно данных»,
  а не ноль, потому что ноль читается как «худший перевозчик», а он всего
  лишь новый.
* Фоновые задачи (`worker/tasks.py`): опрос статусов ежеминутно, сверка
  «призраков» каждые десять минут, пересчёт скора ежесуточно. Два независимых
  заслона: сбой одного отправления не лишает обновлений остальные у того же
  тенанта, сбой одного тенанта не останавливает обход. Оба проверены тестом,
  который краснеет без них — по отдельности, потому что при живом внутреннем
  заслоне внешний не срабатывает вовсе и остался бы непроверенным.
  Приостановленный тенант пропускается: платформа не ходит к перевозчикам
  за того, кто не оплатил.
* Исходящие вебхуки тенанту (FR-3.6): подписки с секретом, показываемым один
  раз, подпись HMAC-SHA256 над временем и телом, постановка событий в очередь
  в той же транзакции, что и изменение отправления, доставка фоновой задачей
  с пятью попытками и экспоненциальной задержкой (1, 5, 25, 125 минут).
  Адрес получателя задаёт клиент, а запрос уходит с нашего сервера — то есть
  это SSRF в чистом виде. Адрес проверяется дважды, при подписке и перед
  каждой отправкой: между этими моментами запись DNS может измениться.
  Отвергаются не-HTTPS, петлевые, частные, link-local и служебные адреса,
  причём проверяются ВСЕ записи имени, а не первая. Перенаправления
  не выполняются: ответ 302 на чужой адрес обошёл бы только что сделанную
  проверку. Окно между проверкой и подключением остаётся — полностью его
  закрывает только подключение по проверенному адресу, и это отдельная работа.
  В теле уведомления нет персональных данных: только номер, статус и трек.
* Экраны кабинета: реестр отправлений с фильтрами и страницами, карточка
  с лентой событий и отменой, перевозчики со скором и расшифровкой. Цепочка
  замкнулась: с экрана расчёта после фиксации решения создаётся отправление.
* Карточка живёт по адресу `/shipments/view?id=…`, а не сегментом пути:
  кабинет собирается статическим экспортом (ADR-0012), а тот требует знать
  все значения динамического сегмента заранее — идентификаторы же появляются
  в рантайме и у каждого тенанта свои.
* Найдено на стенде и исправлено: **созданное отправление не попадало
  в очередь опроса**. `next_poll_at` проставлялся только при приёме событий,
  а первому событию неоткуда было взяться — фоновая задача такое отправление
  не видит, и трекинг не начинался никогда. Тестами не ловилось, потому что
  создание и приём событий проверялись порознь. Закрыто регрессионным тестом.
* Модель снапшотов переехала из `scoring/` в `intelligence/`: карта модулей
  в `CLAUDE.md` называет именно его, а расходиться с ней нельзя. Имя таблицы
  не изменилось, миграции не потребовалось.

* ТЗ v3 в `docs/tz/v3/` (markdown рядом с оригинальными `.docx`), v1 в архив.
* `CLAUDE.md` переписан под v3.
* Объявлены модули `routing/`, `intelligence/`, `billing/`; контрактов
  import-linter стало семь — добавлен запрет `routing` ходить к перевозчикам.

## Не сделано в трекинге и почему

1. **Приём вебхуков от перевозчиков (FR-3.1) — сделано.** Решение принято
   человеком и записано в ADR-0015: узкое окно `app.auth_scope = 'webhook'`
   на поиск отправления по перевозчику и идентификатору заказа, третье
   в ряду после входа пользователя и поиска API-ключа. Подпись проверяется
   секретом того тенанта, чьё отправление названо в теле, — до единой записи
   в базу. Секрет лежит в зашифрованном конверте доступов, поле
   `webhook_secret`.

   Контракт адаптера при этом расширен: `parse_webhook` возвращает
   `list[WebhookUpdate]` с идентификатором заказа, иначе отправление не найти.
   Это `carriers/base.py`, то есть CLAUDE.md §7 пункт 3 — нужно построчное
   ревью.

   Неизвестный заказ отвечает `202`: `404` заставил бы перевозчика повторять
   доставку бесконечно из-за заказа, созданного не через нас.

   Секрет задаётся как необязательное поле доступов (`webhook_secret`):
   кабинет его показывает, скрипт спрашивает и разрешает пропустить. Без него
   перевозчик подключён и работает — просто на опросе; требовать его значило
   бы не дать подключиться тому, кому вебхуки не нужны.

   Разбор конкретного формата СДЭК не написан: `parse_webhook` и
   `verify_webhook` в адаптере по-прежнему отказывают явно. Официальный SDK
   здесь не помогает — он клиент, а не приёмник: в нём есть подписка
   на вебхуки и имя события `ORDER_STATUS`, но не состав тела. Нужны боевые
   доступы и образцы — то же ограничение, что и у остального адаптера.
2. **Фоновые задачи опроса и сверки — сделано.** Ранее здесь было написано,
   что они заблокированы решением по RLS. Это была ошибка: таблица `tenants`
   платформенная и RLS на неё не распространяется, поэтому задача перечисляет
   тенантов и обходит их по одному, открывая на каждого обычную транзакцию
   с установленным тенантом. Новых прав не потребовалось — те же, что
   у HTTP-запроса, и ни правом больше. См. `worker/tasks.py`.

3. **Адресная книга и пользователи в кабинете — сделано.** Экраны
   `/counterparties` и `/users` работают на уже существовавших эндпоинтах
   ядра. Ни того, ни другого пути в `docs/tz/v3/openapi.yaml` нет вовсе,
   поэтому типы клиента написаны руками по `core/schemas.py` — расхождение
   с контрактом, которое исчезнет, когда пути в него попадут.

4. **Публичная страница трекинга (FR-3.5) — не в объёме v3, и вдобавок
   упиралась бы в чтение поперёк тенантов.** Требования нет в v3: слово
   «публичн» встречается там только про публичный API ПЭК и про публичные
   идентификаторы, а не про страницу для получателя без авторизации.
   Если её вернут решением, останется в силе и техническая часть: страница
   открывается по трек-номеру, то есть без тенанта, а найти по нему
   отправление можно только поперёк тенантов — это ADR-0015.

5. **Печать документов (FR-4)** не начинается без решения по зависимостям:
   клиента объектного хранилища и библиотеки PDF в проекте нет, а модель
   `Document` хранит `s3_key`, то есть складывать файлы некуда и генерировать
   нечем. Варианты и вопросы — в ADR-0016.

## Не сделано в Carrier Score и почему

1. **Свод по всем тенантам сразу.** Раздел 10.2 требует приора «среднее
   по платформе», а наблюдения берутся из `shipments` и `delivery_outcomes`
   под `FORCE ROW LEVEL SECURITY`: роль приложения читает только своего
   тенанта. Сглаживание сейчас использует общий приор `PRIOR_WEIGHT = 20`
   без платформенного среднего.

   Решение о принадлежности скора принято (ADR-0017): он **свой у каждого
   тенанта**. Настоящий свод остаётся отдельной задачей и потребует роли,
   читающей поверх тенантов, и правила анонимности — при каком числе тенантов
   и отправлений агрегат перестаёт указывать на конкретного клиента.

2. **Разрезы `direction` и `direction_weight` (FR-7.2).** Каскад разрезов
   реализован и работает, но пока заполняется только `global`. Ключ направления
   в модели описан как пара кодов регионов (`RU-PRI>RU-MOW`), а регион
   в адресе контракта необязателен и в наших снимках сплошь и рядом пуст.
   Строить ключ по названиям городов значило бы дробить и без того малую
   выборку. Нужен ответ, из чего собирать ключ.

3. **Скор в выдаче расчёта — сделано (FR-7.6), после устранения утечки.**
   Проверка показала, что `carrier_score_snapshots` была платформенной:
   без `tenant_id`, без RLS, с уникальностью по перевозчику, разрезу, периоду
   и версии формулы. Пересчёт каждого тенанта перезаписывал одну и ту же
   строку, и `GET /v1/analytics/carriers` отдавал всем статистику того, кто
   считался последним: его долю просрочек, долю инцидентов, индекс цены
   и объём отправлений.

   По решению человека (ADR-0017) снапшот принадлежит тенанту: миграция 0009
   добавила `tenant_id`, RLS с `FORCE` и `tenant_id` в ключ уникальности,
   а старые строки удалены — приписать их кому-либо значило бы выдать чужие
   числа за свои ещё раз.

   После этого `score_at_quote`, `score_confidence` и `score_scope`
   заполняются в момент расчёта и остаются в предложении снимком: следующий
   пересчёт их не двигает. В ответе `insufficient` превращается в `null` —
   такого значения в схеме `RateOffer` нет, и раз числа нет, говорить
   о доверии к нему нечего.

4. **Пересчёт по расписанию (FR-7.1) — сделано.** Задача обходит тенантов
   по одному и считает каждому его собственный скор. Раньше здесь было
   написано, что пересчёт следующего тенанта затирает предыдущий, — так и
   было, и это исправлено миграцией 0009 (см. пункт 3).

## Не сделано в неделе 5 и почему

1. **Адаптер СДЭК не проверен на боевом контуре.** Доступы не получены,
   а домены СДЭК закрыты сетевой политикой окружения разработки (`403`
   на `CONNECT`). Фикстуры синтетические, помечены как таковые. Сверки
   при получении доступов перечислены в ADR-0010; осталось три.

   Единица измерения веса — та самая, где ошибка стоит тысячекратной цены, —
   **подтверждена**: внутри платформы килограммы, в СДЭК уходят граммы,
   как и написано в readme официального SDK. Код менять не потребовалось.
2. **Повторное использование выдачи (FR-1.6) сделано, но не в Redis.**
   Тот же запрос в пределах `valid_until` возвращает сохранённую выдачу
   и не опрашивает перевозчиков заново. Хранилищем выбран сам PostgreSQL,
   а не Redis, по одной причине: в снимке запроса лежат адреса, то есть
   персональные данные, и класть их копию во второе хранилище со своим
   сроком хранения — решение, которого никто не принимал. В базе они уже
   есть и защищены RLS.

   Отбор неточен в одну сторону: перевозчик, ответивший без ошибки, но без
   единого тарифа, не оставляет строк, и набор учётных записей в выдаче
   не совпадёт с текущим — такой запрос будет посчитан заново. Это лишний
   расчёт, а не неверный ответ. Точное сравнение требует хранить состав
   опроса в самой выдаче, то есть колонки в `rate_quotes`, а изменение
   схемы — решение человека (CLAUDE.md §7).
3. **Carrier Score в выдаче отсутствует.** Формула и снапшоты написаны,
   но до выдачи расчёта скор пока не доходит — см. раздел «Не сделано
   в Carrier Score». Его вес в комбинированном ранге по-прежнему
   не перераспределяется на цену, а просто не участвует.
4. **Пакетный расчёт (FR-1.8) — не в объёме v3.** Требование существует
   только в архивном ТЗ v1 (`archive-v1/01-mvp-functional.md`, строка 300):
   `POST /v1/rates/batch`, до 1 000 строк, асинхронно, результат по `job_id`.
   В действующем ТЗ v3 слов «пакетный», «массовый», `batch` нет ни разу,
   и такого пути нет в `openapi.yaml`. По v1 новый код писать нельзя
   (CLAUDE.md §1), поэтому пункт снят с плана. Нужен — верните его решением
   и добавьте путь в контракт.

## Контракт: остался один нереализованный путь

`GET /v1/carriers` объявлен в контракте и не был реализован — кабинет не мог
показать, кто подключён, по чьему договору считается цена и что нужно ввести,
чтобы подключить остальных. Сделано: список всех перевозчиков платформы
с отметкой о подключении тенанта, режимом договора и итогом последней
проверки доступов. **Учётные данные не возвращаются** — только имена полей,
которых требует перевозчик; на это есть отдельный тест, и он краснеет,
если шифротекст попадает в ответ.

Нереализованным остаётся один путь — `POST /v1/webhooks/{carrier_code}`:
тенант неизвестен, пока отправление не найдено по трек-номеру, а найти его
можно только чтением поперёк тенантов (ADR-0015). Список ведётся в
`tests/integration/test_openapi_conformance.py`, и тест краснеет, когда путь
реализован, но из списка не убран, — именно так это и обнаружилось.

## Нумерация FR принадлежит архиву, а не действующему ТЗ

Обнаружено при разборе очереди. В коде 118 ссылок вида `FR-3.6` в 46 файлах,
и в этом файле их не меньше. **Ни одного номера `FR-` в ТЗ v3 нет**: вся
нумерация живёт в `archive-v1/01-mvp-functional.md`. Проверяется одной
командой:

```bash
grep -rc 'FR-' docs/tz/v3/*.md        # везде 0
grep -c  'FR-' docs/tz/archive-v1/01-mvp-functional.md   # 80
```

Само по себе это не ошибка: CLAUDE.md §1 прямо говорит, что v1 объясняет,
каким требованиям отвечает старый код. Ссылки в коде читаются как история
и переписывать их незачем.

Ошибка — планировать по этим номерам новую работу. Именно так в очереди
оказались два пункта, которых действующее ТЗ не требует: пакетный расчёт
и публичная страница трекинга. Оба сняты, оба помечены как возвращаемые
только решением человека.

**Правило на будущее:** прежде чем брать пункт из этого файла, проверьте,
что требование есть в v3 — по смыслу, а не по номеру. Номера в v3 нет.

### Сырьё вызовов не пишется вовсе

Найдено при написании `purge_raw_calls`. Удаление по сроку сделано и покрыто
тестами, но **удалять пока нечего: в `carrier_raw_calls` не пишет ни одна
строка кода.** Проверено поиском по `CarrierRawCall(` — конструктор модели
не вызывается нигде, кроме её объявления.

Цепочка почти собрана: `CarrierHttpClient.request` принимает
`on_raw_call`, клиент СДЭК его пробрасывает — а адаптер не передаёт, потому
что взять его неоткуда. Чтобы домен дал адаптеру приёмник, приёмник должен
попасть в него через `carriers/base.py`: либо полем в DTO `CarrierAccount`,
либо параметром конструктора адаптера. И то и другое — **контракт
`CarrierAdapter`, то есть CLAUDE.md §7, пункт 3**: решение человека.

Пока этого нет:

* разбирать спорную ситуацию с перевозчиком нечем — сырого ответа не осталось;
* `data_quality` в Carrier Score считается без него;
* тридцатидневный срок хранения формально соблюдается тем, что хранить нечего.

Последнее — не повод откладывать: как только сырьё начнёт писаться, удаление
уже будет работать.

## Требует решения человека

0. **Верификатор TOTP — вход по второму фактору сейчас закрыт наглухо.**

   Ревью безопасности нашло, что прежняя проверка принимала **любую** строку
   из шести символов как успешный второй фактор: код ни с чем не сравнивался,
   `users.mfa_secret` не читался ни одной строкой кода, библиотеки TOTP
   в зависимостях нет. Защиты не было именно в том случае, ради которого
   двухфакторная аутентификация и существует, — когда пароль уже украден.

   Сейчас `AuthService.login` **отказывает во входе** любому пользователю
   с `mfa_enabled = true` (`_refuse_unverifiable_second_factor`). Это
   осознанно: молча пропускать хуже, чем отказать.

   **Когда это придётся решать.** Заглушка не мешает ровно до тех пор, пока
   никому не включена MFA. Она станет блокирующей в первый же из моментов:

   * появится экран или эндпоинт включения второго фактора;
   * пилотный клиент потребует 2FA (продуктовое ТЗ называет её обязательной
     для роли `owner`, сейчас это лишь `log.warning`);
   * до боевого запуска — вход владельца без второго фактора выпускать нельзя.

   **Что нужно от человека:** выбор библиотеки TOTP — новая зависимость,
   а это решение человека с записью в ADR (CLAUDE.md §2). После него:
   сверка кода с `mfa_secret`, защита от повторного использования шага,
   путь включения и восстановления, тест «неверный код даёт 401».

1. **Доступы СДЭК** (`client_id`, `client_secret` в ЛК «Роспломбы»).
   Адаптер написан и покрыт тестами, но на боевом контуре не проверен:
   без доступов нельзя записать реальные фикстуры и сверить единицу
   измерения веса. Список обязательных сверок — в ADR-0010.
2. **Ключ ДаData** — блокирует неделю 3.
3. **VPS и S3 в РФ** — нужны до первого деплоя.
4. **Производственный календарь РФ на 2026 год** — файл
   `backend/src/aerogram/shared/data/production_calendar_ru.yaml` заполнен базовыми
   праздниками ТК РФ, переносы помечены `verified: false`. Без сверки с постановлением
   фактический срок доставки считается приблизительно.
5. **Построчное ревью миграций и RLS** — требование CLAUDE.md §7. Файлы:
   `alembic/versions/20260829_0001_initial_schema.py`,
   `20260829_0002_tenant_isolation.py`, `20260829_0003_app_role_grants.py`,
   `20260829_0004_directories_week3.py`.
6. **ADR-0004** (окно поиска пользователя при входе) — осознанный компромисс,
   требует подтверждения.
7. **Источник тарифа ПЭК не укладывается в контракт.** Схема `RateOffer.source`
   в `openapi.yaml` имеет ровно два значения — `client_contract` и `logistics_os`.
   Но бэкенд-ТЗ, раздел 11, требует для ПЭК «separate public vs contract source
   explicitly»: публичный расчёт ПЭК не является ни договором клиента, ни
   тарифом платформы. Сейчас такой источник даёт `NULL`, а не выдумку.
   Варианты: считать публичный расчёт разновидностью `logistics_os`, либо
   добавить в контракт третье значение. Решать до написания адаптера ПЭК.

8. **Преобразование цены в `price_index` (Carrier Score).** Раздел 10.1
   требует «нормированное положение цены относительно медианы, обрезанное
   в [0; 1]», но точного вида не задаёт. Выбрано так: ровно по медиане —
   половина шкалы, вдвое дешевле — единица, вдвое дороже — ноль. Центр
   в 0.5, а не в 1, потому что иначе все, кто дешевле медианы, получали бы
   одинаковый максимум и переставали различаться. Требует подтверждения
   вместе с весами формулы: изменение вида обязано менять `FORMULA_VERSION`.

9. **Веса «оптимального» выбора** (`routing/strategies.py`, `OPTIMAL_WEIGHTS`).
   Сейчас цена 0.40, срок 0.30, надёжность 0.20, риск 0.10 — рабочее начальное
   приближение, а не обоснованная бизнесом величина. CLAUDE.md §7, пункт 8:
   формула рекомендации требует решения человека. Пересмотр весов обязан
   менять `ALGORITHM_VERSION`, иначе исторические рекомендации станут
   несопоставимыми.

10. **Язык условий и действий правил маршрутизации.** Таблица `routing_rules`
   создана, `conditions` и `actions` — JSONB, но ТЗ v3 не определяет их состав.
   Сочинять язык правил без спецификации я не стал: сейчас правила влияют
   только на `policy_version` в снимке рекомендации. Нужен состав условий
   (перевозчик, направление, вес, стоимость груза) и действий (запретить,
   разрешить, порог страхования, автовыбор).

11. **`tenant_id` без внешнего ключа на `tenants`.** Все 16 таблиц из миграции
   0001 имеют индекс по `tenant_id`, но не имеют FK. Новые таблицы Decision
   Engine сделаны так же — ради единообразия схемы, а не потому, что так лучше.
   FK защитил бы от строк-сирот; добавление его — миграция на 21 таблицу
   и решение уровня CLAUDE.md §7.

12. **Отправления: три расхождения с контрактом.**

    *Отмены в контракте нет.* FR-2.6 её требует, в `openapi.yaml` пути нет.
    Реализована как `POST /v1/shipments/{id}/cancel` и объявлена служебной
    в тесте соответствия. Нужно либо дополнить контракт, либо отказаться
    от требования; молча не делать — худший вариант, без отмены заказ
    у перевозчика живёт своей жизнью.

    *Словарь статусов беднее нашего.* ТЗ, раздел 9, требует четырнадцати
    состояний, схема `Shipment` перечисляет десять. Перевод на границе API
    идёт с потерями: «возврат» и «неудачная попытка вручения» превращаются
    в `Exception`, хотя это разные события с разными последствиями
    для клиента. Внутри они по-прежнему различимы.

    *`external_id` означает в контракте две разные вещи.* В `Shipment` это
    идентификатор заказа у перевозчика (бэкенд-ТЗ, раздел 5), а в
    `CreateShipmentRequest` клиент прислать его не может — заказа ещё нет.
    Принято читать его как номер клиента в его системе: если он задан,
    он становится номером отправления. Ответ при этом отдаёт в том же поле
    идентификатор ТК. Одно имя для двух смыслов рано или поздно укусит.

13. **Построчное ревью создания отправления** — требование CLAUDE.md §7,
    пункт 4 (идемпотентность и сверка «призраков»). Решения, принятые мной
    и требующие подтверждения: черновик пишется отдельной транзакцией
    (второе соединение на время создания); номер выводится из ключа
    идемпотентности, а не выдаётся случайно; повтор с тем же ключом
    и другим телом сверяется по полям строки, а не по хешу тела —
    отдельной колонки под отпечаток нет.

14. **Два поля рекомендации расходятся со схемой контракта**, и оба
    расхождения идут от прозы того же ТЗ. `confidence` в схеме
    `Recommendation` отсутствует, но системное ТЗ, раздел 9, требует явно
    показывать низкую уверенность, а фронт-ТЗ, раздел 4, помещает её
    в карточку. `recommended_offer_id` в схеме обязателен и не допускает
    null, но когда в срок не укладывается никто, рекомендации нет.
    Нужно либо дополнить контракт, либо изменить требование.

15. **Лицензия справочника городов** — вынесена в раздел «Перед выпуском MVP»
   ниже. Продукт работает без неё: `cities` наполняется лениво из подсказок
   ДаData, механизм реализован и покрыт тестами.

## Перед выпуском MVP

Список того, что обязано быть закрыто до боевого запуска. В отличие от
задач разработки, здесь почти всё требует решения человека, а не кода,
и почти всё дешевле закрыть заранее, чем задним числом.

### 1. Лицензия справочника городов — РЕШИТЬ ДО ЗАПУСКА

Официальный справочник городов ДаData `github.com/hflabs/city` (1117 городов,
ровно те поля, что нужны модели `City`) распространяется под
**CC-BY-SA 4.0**. Лицензия требует указания авторства и распространяет
условие share-alike на производные базы данных. Что это означает для
коммерческого SaaS с закрытым кодом — вопрос к юристу, а не к разработчику.

Соседний датасет `hflabs/settlement-fias-guid` (160 тыс. населённых пунктов)
использовать **нельзя вовсе**: его лицензия прямо запрещает коммерческое
применение.

Варианты:

| Вариант | Что даёт | Чего стоит |
|---|---|---|
| Юридическая оценка CC-BY-SA и включение справочника | Мгновенный старт: 1117 городов в базе с первого дня, подсказки работают без ДаData | Консультация юриста; возможное требование раскрыть производную базу |
| Ленивое наполнение из ДаData (**реализовано сейчас**) | Никаких правовых вопросов; города появляются по факту обращения | Первые обращения к новому городу требуют доступности ДаData; локальные подсказки на старте пусты |
| Выгрузка ГАР/ФИАС с сайта ФНС | Первоисточник, свободные условия | Объём в десятки гигабайт и своя загрузка — недели работы |

**Текущее состояние: выбран второй вариант**, продукт работает без справочника.
Решение нужно принять до момента, когда лимит ДаData станет узким местом.

### 2. Производственный календарь РФ на 2026 год

`backend/src/aerogram/shared/data/production_calendar_ru.yaml` заполнен базовыми
нерабочими днями по ТК РФ, переносы помечены `verified: false`. Без сверки
с постановлением Правительства фактический срок доставки считается
приблизительно, а через него — Carrier Score.

### 3. Юридический пакет по персональным данным

Раздел 12.2 ТЗ: уведомление в Роскомнадзор об обработке ПДн, политика
обработки, согласия и поручения на обработку в договоре с тенантом.
Готовится параллельно разработке, к запуску обязан быть.

### 4. Внешнее тестирование на проникновение

Раздел 12.9 ТЗ: перед промышленным запуском. Отдельно проверить публичную
страницу трекинга — единственную точку без авторизации.

### 5. Проверка восстановления из бэкапа

`deploy/backup-restore-test.sh` написан, но ни разу не выполнялся на боевых
