# Состояние работ

> **30 августа 2026: пришло ТЗ v3, продукт переопределён.**
> Центром стал Decision Engine, перевозчиков пять вместо одного, деньги переходят
> в минорные единицы, фронт — на Next.js. Решение по итогам разбора: **переделываем
> этот репозиторий, а не начинаем новый** — сохраняется около двух третей бэкенда.
> Разбор расхождений и план — раздел «Переход на ТЗ v3» ниже.
> Всё, что описано в разделе «Готово», написано по ТЗ v1 (`docs/tz/archive-v1/`)
> и читать его нужно с этой поправкой.

Обновляется по завершении каждого этапа плана.

* Одна миграция `0004_directories_week3`, обратимость проверена.

### Ревью миграций (требование CLAUDE.md §7)

Построчное ревью схемы нашло три дефекта, все исправлены:

* **Замороженные значения по умолчанию.** В миграции 0001 восемь колонок
  времени получили `server_default`, заданный питоновской строкой `"now()"`
  вместо `sa.text("now()")`. PostgreSQL вычислил его один раз при миграции,
  и `DEFAULT` стал литералом с моментом выполнения. Доказано: две записи
  в `audit_log` с разницей в секунду получили одинаковый штамп. Аудит-лог
  (12.6 ТЗ) переставал быть доказательством. Починено миграцией 0005,
  всем колонкам добавлено питоновское значение по умолчанию, регрессия
  закрыта тестом.
* **Мёртвый индекс** `ix_counterparties_tenant_id_inn`: планировщик не
  выбирает его никогда, точное сравнение обслуживает индекс по префиксу ИНН.
  Удалён.
* **Дубль индекса**, созданный мной же в 0004: `ix_counterparties_tenant_id_name`
  полностью перекрывается частичным `ix_counterparties_tenant_id_alive`.
  Удалён старый.

Дополнительно: все индексы, включая частичные и по выражениям, объявлены
в моделях — иначе автогенерация следующей миграции предложила бы их удалить.
После этого `alembic check` перестал шуметь и добавлен в CI вместе
с проверкой «голова миграций одна».

### Неделя 5 — расчёт по API СДЭК

* Клиент СДЭК: OAuth `client_credentials`, кэш токена в памяти процесса
  с запасом перед истечением, однократная переавторизация при отзыве токена,
  защита от параллельных авторизаций одной учётной записью.
* `quote`: расчёт по доступным тарифам, нормализация тарифов, фильтрация
  выдачи по режиму доставки, разбор ошибок перевозчика в доменные.
* `fetch_refs`: выгрузка городов СДЭК с их кодами.
* Rate shopping (`POST /api/v1/rates`): параллельный опрос учётных записей
  тенанта, таймаут на перевозчика и общий дедлайн (FR-1.3), неответившие —
  отдельными строками выдачи (FR-1.4), сохранение запроса и котировок
  вместе с сырьём (FR-1.7), комбинированный ранг (FR-5.3, FR-5.4).
* Контракт СДЭК сверен с исходниками официального SDK (ADR-0010).

Две ошибки, найденные тестом уже по написанному коду:

* нечитаемые учётные данные ОДНОГО перевозчика роняли весь расчёт: расшифровка
  бросает `InvalidTag` из cryptography, а перехватывался только `ValueError`.
  Это прямое нарушение FR-1.4 — ошибка одного перевозчика не должна ронять
  выдачу;
* список задач опроса фильтровался, а индекс для строки таймаута брался
  из нефильтрованного списка: при пропуске одной учётной записи строка
  «не ответил» назвала бы чужого перевозчика.

## Переход на ТЗ v3

### Что сохраняется

| Модуль | Строк | Судьба |
|---|---:|---|
| `carriers/` — контракт, HTTP-слой, реестр, карты статусов | 1026 | Сохраняется: ТЗ v3 §9 требует те же методы плюс `health_check` |
| `core/` — тенанты, RBAC, JWT, аудит, шифрование | 1376 | Сохраняется: §2 требует ровно это |
| `directories/` — лестница ФИАС, city_carrier_map | 1636 | Сохраняется: §7 требует mapping-таблицу городов |
| `shared/` | 714 | Сохраняется, кроме модуля денег |
| `rating/` | 624 | Механика fan-out сохраняется, DTO и ранжирование переписываются |
| Тесты | 3636 | Сохраняются |
| `frontend/` | 519 | Выбрасывается: ТЗ требует Next.js |

Изоляция тенантов у нас **строже требований**: ТЗ v3 просит проверять tenant scope
в service/repository, у нас RLS на уровне PostgreSQL и роль без `BYPASSRLS`.
Не переделываем, оставляем как есть.

### Что ломается

1. **Деньги.** `NUMERIC(12,2)`/`Decimal` → `BIGINT amount_minor` + `CHAR(3) currency`
   (backend ТЗ §4, схема `Money` в OpenAPI, фронт §10). ADR-0011.
2. **Нет ядра нового продукта.** `Recommendation`, `Decision`, `DeliveryOutcome`,
   `CostComponent`, `RoutingRule` — достройка модулей `routing/`, `intelligence/`,
   `billing/`, а не переделка существующих.
3. **Major Express первым, SOAP/WSDL.** Новая зависимость `zeep`, ADR-0013.
4. **Контракт API** переписывается под `docs/tz/v3/openapi.yaml`: пути `/v1/*`,
   плоский `address_line` вместо `city_fias_id`, `weight_grams`/`length_mm`.
5. **Фронт** на Next.js, ADR-0012.

### Ревью безопасности

Отдельный проход по аутентификации, RLS, криптографии и инъекциям. Четыре
находки прошли независимую проверку на ложное срабатывание; две отсеялись
как невстроенные функции, а не обход существующего контроля. Одна из них,
**область действия API-ключей**, перестала быть невстроенной вместе
с появлением выпуска ключей и теперь проверяется (ADR-0019): пока выпустить
ключ было нельзя, поле было мёртвым, а с выпуском в кабинете оно стало бы
обещанием, которого ничто не поддерживает. Приостановка тенанта по-прежнему
не встроена. Две подтверждены и закрыты:

* **Обход второго фактора.** Принималась любая строка из шести символов.
  Сначала вход с `mfa_enabled = true` был закрыт наглухо, затем появился
  настоящий верификатор на PyOTP (ADR-0018): код сверяется с секретом,
  секрет хранится зашифрованным, один шаг принимается один раз. Открытым
  остаётся восстановление доступа — пункт 0 раздела «Требует решения человека».
* **Подъём привилегий через границу тенанта.** `UserCreate.role` принимал
  полный `UserRole`, включая `platform_admin`, а `POST /v1/users` открыт
  владельцу любого тенанта. Владелец мог выдать себе платформенную роль
  и через `/v1/admin/city-mappings/*` испортить `city_carrier_map` —
  таблицу без `tenant_id` и без RLS, которая читается на расчёте у всех
  тенантов сразу. Теперь тело запроса типизировано `TenantRole`, где
  платформенных ролей нет физически, плюс второй барьер в `UserService.create`.

Признано здоровым: покрытие RLS полное на всех 22 таблицах с `tenant_id`;
оба окна `app.auth_scope` только на SELECT, транзакционные, с разными
значениями; инъекций нет; SSRF нет; криптография корректна; обработчики
ошибок не протекают.

Побочная функциональная находка, тоже исправлена: `ApiKeyService.resolve`
вызывала `touch_used` до установки тенанта, поэтому под RLS `UPDATE`
не находил строк и `last_used_at` не записывался никогда. Отметка вынесена
в `mark_used` и вызывается после `set_tenant` — тем же порядком, что и работа
с пользователем в ветке JWT.

### Ревью и прогон тестера

Полный прогон обоих разделов плюс построчное ревью ветки нашли девять
дефектов. Все исправлены и закрыты тестами.

Три ломали продукт в бою:

* **Аутентификация по API-ключу не работала вовсе.** Тенант определяется
  по ключу, значит на момент поиска `app.tenant_id` не установлен, а политика
  `tenant_isolation` на `api_keys` объявлена с `FORCE` и не отдаёт строк.
  Любой запрос с `X-Api-Key` получал «Ключ недействителен». Комментарий
  в репозитории ссылался на класс `ApiKeyAuthService`, которого никогда
  не существовало, и ни один тест этот путь не покрывал. Починено миграцией
  0008 — узкое окно только на SELECT, по образцу входа (ADR-0004).
* **Дедлайн без часового пояса ронял расчёт в 500.** Наивный момент вычитался
  из момента с зоной. Теперь отвергается на границе с указанием, что прислать:
  достроить зону значило бы выбрать её за клиента, а для Москва → Владивосток
  разница в семь часов решает, уложился ли перевозчик.
* **Регион из одних пробелов или точки ронял расчёт в 500**: первое слово
  бралось по индексу из пустого списка.

Три искажали данные, ради которых продукт существует:

* **Повтор решения создавал второе решение.** Ключ идемпотентности создавался
  внутри мутации, то есть заново на каждую попытку. Теперь живёт столько же,
  сколько намерение оператора, и сбрасывается новым расчётом.
* **Предложение без даты обнуляло вес срока в «оптимальном».** Сентинел
  `10**12` растягивал шкалу на века, и разница между реальными сроками
  схлопывалась в ноль.
* **`no_deadline_match` ставился, когда просто никто не ответил.** «Никто
  не успевает» требует показать альтернативы, «никто не ответил» — разобраться
  с доступностью; в снимке они были неразличимы.

Остальные три: клиент по API-ключу не мог зафиксировать решение (нарушал
ограничение схемы и получал невнятный 409 вместо указания прислать
`mode="auto"`); проверка в E2E не ждала ответа и потому никогда не срабатывала;
при переходе на Next.js потерялся `eslint-plugin-react-hooks`, и нарушения
правил хуков перестали ловиться.

Отдельно: E2E переведены с `next dev` на продакшн-сборку. Dev-сервер после
правок файлов уходит в `__webpack_modules__ is not a function`, страница
перестаёт гидрироваться, и тест проверяет не то, что отгружается.

### Сделано в переходе

* Сущности Decision Engine: `rate_offers` с `cost_components`, `recommendations`,
  `decisions`, `delivery_outcomes`, `routing_rules`; RLS на всех пяти новых
  таблицах, миграция `0007_decision_engine`, обратимость проверена.
* Переименование по контракту: `rate_requests` → `rate_quotes` (снимок запроса),
  `rate_quotes` → `rate_offers` (предложение). В ЭРД и OpenAPI «quote» — это
  запрос, а не предложение; расхождение имён кода и контракта пришлось бы держать
  в голове у каждого, кто читает и то и другое.
* Routing Engine: четыре стратегии, факты объяснения, `POST /v1/routing/quote`
  и `POST /v1/decisions` с обязательным `Idempotency-Key`.
* API приведён к `docs/tz/v3/openapi.yaml`; тест соответствия сторожит
  расхождения и ведёт список ещё не реализованных путей.
* Фронт переписан на Next.js (ADR-0012): вход и экран Rate Shopping —
  стратегии, карточка рекомендации с объяснением, расшифровка стоимости,
  диалог override, признаки stale quote и partial failure. Клиент API
  генерируется из `docs/tz/v3/openapi.yaml`.
* Неизменяемость решения — триггером в БД, а не соглашением в коде: приложение
  обходится скриптом, триггер нет.
* Отправления: `POST /v1/shipments` с обязательным `Idempotency-Key`, список
  с фильтрами контракта, карточка, отмена. Миграции не потребовалось — схема
  недели 2 содержала всё нужное.
* **Защита от «призраков» (FR-2.5)** построена на трёх свойствах, и ни одно
  не работает без остальных. Черновик коммитится **своей транзакцией до**
  обращения к перевозчику: транзакция запроса откатилась бы вместе с ним
  ровно тогда, когда запись о намерении нужна больше всего. Отсюда главное
  следствие — если строки нет, то и обращения к ТК не было, и на свежем
  черновике сверять нечего. Номер выводится из ключа идемпотентности и уходит
  перевозчику как номер клиента. Повтор начинается со сверки: адаптер
  спрашивает ТК о заказе с нашим номером, и найденный заказ принимается
  в базу, а не создаётся второй.
  Каждое из трёх свойств проверено тестом, который краснеет без него: без
  отдельной транзакции черновик исчезает вместе с ответом, без сверки повтор
  создаёт у перевозчика второй заказ на тот же груз.
* Отмена черновика тоже идёт через сверку: бросить заказ, о котором мы
  не знаем, — это и есть призрак.
* Трекинг: единая лента событий (`GET /v1/shipments/{id}/tracking`),
  нормализация статусов по YAML-картам, дедупликация по отпечатку события,
  проекция на отправление, `DeliveryOutcome` и адаптивное расписание опроса
  по таблице FR-3.2. Модуль сознательно **не ходит к перевозчикам**: он
  принимает уже полученные события, а опрос делает `shipments`, где адаптер
  и расшифрованные доступы уже есть.
  Два свойства проверены тестом, который краснеет при правдоподобной ошибке —
  сортировке ленты по времени получения вместо времени события: она показала
  бы доставку раньше отправки и откатывала бы статус назад догоняющим старым
  событием. Дедупликация проверена так же: без неё повторное событие роняет
  всю пачку на уникальном индексе.
* Отсутствие карты статусов перевозчика больше не роняет приём событий:
  событие сохраняется с сырым статусом и признаком «не сопоставлено», то есть
  попадает в очередь ручного разбора. Сам загрузчик карт по-прежнему бросает
  исключение — это ошибка настройки, и молчать о ней нельзя.
* `eta` и `deadline` в ответе об отправлении заполняются из снимка расчёта
  пакетным запросом: оператору важно не «когда обещали», а «успеваем ли».
* Carrier Score: формула раздела 10.1 (`intelligence/score.py`), байесовское
  сглаживание с приором 20, пороги доверия FR-7.3, снапшоты с версией формулы
  и `GET /v1/analytics/carriers` с расшифровкой по компонентам (FR-7.5).
  Формула вынесена в отдельный модуль без зависимостей намеренно: это тот код,
  где ошибка не падает, а тихо меняет советы, которые продукт даёт клиенту.
  Холодный старт закрыт так, как требует раздел 10.2: при выборке меньше
  десяти скор не считается вовсе — наружу уходит «недостаточно данных»,
  а не ноль, потому что ноль читается как «худший перевозчик», а он всего
  лишь новый.
* Фоновые задачи (`worker/tasks.py`): опрос статусов ежеминутно, сверка
  «призраков» каждые десять минут, пересчёт скора ежесуточно. Два независимых
  заслона: сбой одного отправления не лишает обновлений остальные у того же
  тенанта, сбой одного тенанта не останавливает обход. Оба проверены тестом,
  который краснеет без них — по отдельности, потому что при живом внутреннем
  заслоне внешний не срабатывает вовсе и остался бы непроверенным.
  Приостановленный тенант пропускается: платформа не ходит к перевозчикам
  за того, кто не оплатил.
* Исходящие вебхуки тенанту (FR-3.6): подписки с секретом, показываемым один
  раз, подпись HMAC-SHA256 над временем и телом, постановка событий в очередь
  в той же транзакции, что и изменение отправления, доставка фоновой задачей
  с пятью попытками и экспоненциальной задержкой (1, 5, 25, 125 минут).
  Адрес получателя задаёт клиент, а запрос уходит с нашего сервера — то есть
  это SSRF в чистом виде. Адрес проверяется дважды, при подписке и перед
  каждой отправкой: между этими моментами запись DNS может измениться.
  Отвергаются не-HTTPS, петлевые, частные, link-local и служебные адреса,
  причём проверяются ВСЕ записи имени, а не первая. Перенаправления
  не выполняются: ответ 302 на чужой адрес обошёл бы только что сделанную
  проверку. Окно между проверкой и подключением остаётся — полностью его
  закрывает только подключение по проверенному адресу, и это отдельная работа.
  В теле уведомления нет персональных данных: только номер, статус и трек.
* Экраны кабинета: реестр отправлений с фильтрами и страницами, карточка
  с лентой событий и отменой, перевозчики со скором и расшифровкой. Цепочка
  замкнулась: с экрана расчёта после фиксации решения создаётся отправление.
* Карточка живёт по адресу `/shipments/view?id=…`, а не сегментом пути:
  кабинет собирается статическим экспортом (ADR-0012), а тот требует знать
  все значения динамического сегмента заранее — идентификаторы же появляются
  в рантайме и у каждого тенанта свои.
* Найдено на стенде и исправлено: **созданное отправление не попадало
  в очередь опроса**. `next_poll_at` проставлялся только при приёме событий,
  а первому событию неоткуда было взяться — фоновая задача такое отправление
  не видит, и трекинг не начинался никогда. Тестами не ловилось, потому что
  создание и приём событий проверялись порознь. Закрыто регрессионным тестом.
* Модель снапшотов переехала из `scoring/` в `intelligence/`: карта модулей
  в `CLAUDE.md` называет именно его, а расходиться с ней нельзя. Имя таблицы
  не изменилось, миграции не потребовалось.

* ТЗ v3 в `docs/tz/v3/` (markdown рядом с оригинальными `.docx`), v1 в архив.
* `CLAUDE.md` переписан под v3.
* Объявлены модули `routing/`, `intelligence/`, `billing/`; контрактов
  import-linter стало семь — добавлен запрет `routing` ходить к перевозчикам.

## Делитель объёмного веса — свой у каждого перевозчика

Формула международная и одна для всех, включая авиа: объёмный вес равен
Д × Ш × В (см), делённым на коэффициент; платят по большему из двух весов,
фактического и объёмного. Расходятся не формулы, а **коэффициенты**.

Что известно (со слов заказчика, 31 августа 2026):

* ориентир отрасли — **6000** от IATA: 6000 см³ приравниваются к килограмму;
* встречается запись через объём в кубометрах: м³ × **167**. Это то же самое:
  1 м³ = 1 000 000 см³, делённые на 6000, дают 166,7 кг;
* **не все следуют 6000.** Часть перевозчиков применяет **5000** — объёмный
  вес при этом получается выше, и за объёмный груз берут больше;
* коэффициент может зависеть от политики перевозчика, типа груза
  и направления.

**Отсюда вывод: коэффициент прописывается у каждого перевозчика,
подключаемого к системе.** Так схема и устроена — `carriers.volumetric_divisor`,
своё значение на перевозчика; в коде зашита только величина по умолчанию.

По умолчанию стоит **5000**, и это осознанный выбор в сторону осторожности:
меньший делитель даёт больший объёмный вес, то есть более высокую котировку.
Занижение стоит нам денег напрямую — счёт от перевозчика приходит по его
коэффициенту, а не по нашему.

| Перевозчик | Коэффициент | Откуда значение |
|---|---:|---|
| Major Express | 5000 (по умолчанию) | не подтверждён тарифом |
| СДЭК | 5000 (по умолчанию) | в нашем расчёте не участвует — СДЭК считает объёмный вес сам |
| Деловые Линии | 5000 (по умолчанию) | не подтверждён тарифом |
| ПЭК | 5000 (по умолчанию) | не подтверждён тарифом |
| Яндекс Доставка | 5000 (по умолчанию) | не подтверждён тарифом |

Заполняется по мере получения тарифов. Значение ставится скриптом:

```bash
uv run python scripts/set_volumetric_divisor.py --list
uv run python scripts/set_volumetric_divisor.py --carrier dellin --divisor 6000
```

До записи он показывает, во что коэффициент превращается на трёх посылках,
и предупреждает о значении вне диапазона 1000–10000: ошибка в порядке величины
даёт цену в десять раз больше. Текущее значение видно в кабинете, на экране
перевозчиков, — чтобы расхождение с тарифом заметил человек, а не счёт
от перевозчика через месяц.

**Чего схема пока не умеет.** Коэффициент один на перевозчика. Если он
зависит от типа груза, направления или конкретного тарифа — а такое, по словам
заказчика, встречается, — понадобится хранить его на уровне тарифа или
учётной записи тенанта. Это изменение схемы, то есть решение человека
(CLAUDE.md §7). До него платформа исходит из одного коэффициента
на перевозчика.

### Кто применяет формулу: мы или перевозчик

Вопрос отдельный от коэффициента и такой же денежный. Посчитаем за того, кто
считает сам, — двойной учёт объёма и молчаливое завышение; не посчитаем
за того, кто не считает, — занижение и расхождение со счётом.

| Перевозчик | Считает объёмный вес сам | Что принимает | Основание |
|---|---|---|---|
| СДЭК | да | места: вес в **граммах**, габариты в **сантиметрах** | официальный SDK, `PackageTrait`: «общий вес (в граммах)», «Длина (в сантиметрах)»; расчёт тарифа принимает те же места |
| Деловые Линии | да, по всем признакам | суммарный вес в **кг**, объём в **м³**, максимальные габариты | сторонний адаптер `@opsregistry/adapter-dellin`: считает `totalVolume` в кубометрах из габаритов и отдаёт его перевозчику |
| ПЭК | да, по всем признакам | габариты в **метрах**, объём в **м³**, вес в **кг** | сторонний адаптер `@opsregistry/adapter-pecom`: делит сантиметры на 100 и объём на 1 000 000 |
| Major Express | предполагается, что да | — | адаптер-заглушка, не проверено |
| Яндекс Доставка | **неизвестно** | — | SDK не найден |
| КСЭ, Пони Экспресс | **неизвестно** | — | SDK в npm не найдены |

**О качестве источников.** По СДЭК это официальный SDK — та же планка, что
задаёт ADR-0010. По Деловым Линиям и ПЭК — **сторонние** адаптеры из npm,
а не официальные библиотеки: они показывают форму запроса, но подтверждением
не являются. При подключении этих перевозчиков вопрос проверяется по их
документации и первому же боевому расчёту.

Домены самих перевозчиков закрыты сетевой политикой окружения разработки
(`403` на `CONNECT`); публичные репозитории GitHub и npm доступны, ими
и проверялось.

**Единицы у всех разные** — сантиметры и граммы у СДЭК, метры и кубометры
у ПЭК и Деловых Линий. Наш DTO места несёт сантиметры и килограммы, перевод
делает адаптер. Это обязательный пункт при написании каждого адаптера,
наравне с единицей веса и форматом ошибок.

Умолчание в контракте адаптера стоит в безопасную сторону —
`computes_volumetric_weight = True`, «считает сам», — и на это есть тест.
Выбор такой, потому что завышение заметить труднее занижения: клиент
не жалуется на то, чего не видит, а расхождение со счётом всплывает
и разбирается. Перевозчик, который объёмный вес не считает, обязан объявить
это явно, и тогда платформа досчитает его сама.

## Расчётный вес доходил не до всех

Найдено при разговоре о единице веса. `chargeable_weight` и `volumetric_weight`
были написаны и покрыты тестами, `carriers.volumetric_divisor` лежал
в справочнике — **и всё это никем не вызывалось**: расчёт всегда отправлял
перевозчику фактический вес.

Для СДЭК это было безвредно: он объявляет `computes_volumetric_weight=True`
и считает объёмный вес сам по нашим габаритам. Для любого следующего
перевозчика, который так не умеет, это означало бы цену по фактическому весу
при счёте по объёмному — молча и в нашу сторону убытка.

Теперь подмена делается в `rating`, по способности адаптера: платят
по большему из двух весов, объёмный считается как Д × Ш × В (см) / делитель
перевозчика (по умолчанию 5000). Тому, кто считает сам, вес не подменяется —
иначе объём был бы учтён дважды. Габариты в контракте необязательны;
отсутствующий даёт 1 см, поэтому объёмный вес такого места ничтожен
и максимум остаётся за фактическим — отсутствие габаритов никогда
не завышает цену.

## Нумерация FR принадлежит архиву, а не действующему ТЗ

Обнаружено при разборе очереди. В коде 118 ссылок вида `FR-3.6` в 46 файлах,
и в этом файле их не меньше. **Ни одного номера `FR-` в ТЗ v3 нет**: вся
нумерация живёт в `archive-v1/01-mvp-functional.md`. Проверяется одной
командой:

```bash
grep -rc 'FR-' docs/tz/v3/*.md        # везде 0
grep -c  'FR-' docs/tz/archive-v1/01-mvp-functional.md   # 80
```

Само по себе это не ошибка: CLAUDE.md §1 прямо говорит, что v1 объясняет,
каким требованиям отвечает старый код. Ссылки в коде читаются как история

Ошибка — планировать по этим номерам новую работу. Именно так в очереди
оказались два пункта, которых действующее ТЗ не требует: пакетный расчёт
и публичная страница трекинга. Оба сняты, оба помечены как возвращаемые
только решением человека.

**Правило на будущее:** прежде чем брать пункт из этого файла, проверьте,
что требование есть в v3 — по смыслу, а не по номеру. Номера в v3 нет.

## Расписание зовёт задачи, которых нет

Найдено при работе над FR-8.3. В `worker/app.py` объявлено расписание
на семь задач, а реализованы четыре. Beat будет ставить в очередь имена,
которых воркер не знает, и получать `NotRegistered` — молча для оператора
и с видом, будто функция работает:

| Задача в расписании | Что должна делать | Состояние |
|---|---|---|
| `purge_raw_calls` | Удалять сырьё вызовов ТК старше 30 суток (раздел 8.2 ТЗ, CLAUDE.md §6) | **написана** |
| `detect_delivery_risk` | Список отправлений с риском срыва срока (С-4) | не написана |
| `send_daily_digest` | Ежесуточная сводка тенанту | не написана |

Две оставшиеся — отдельные задачи со своими решениями (что именно считать
риском срыва, куда и в каком виде уходит сводка), поэтому здесь они только
названы.

**Проверка появилась** — `tests/unit/test_worker_schedule.py`. Раньше здесь
было написано, что такой тест был бы красным; это верно только для наивного
варианта. Тем же приёмом, что уже принят для путей контракта, ненаписанное
перечисляется явно: тест краснеет, когда в расписании появляется имя, которого
нет и которое не объявлено, когда объявленное написали и забыли убрать
из списка, и когда написанную задачу никто не ставит в очередь. Ровно эти три
случая и порождали молчаливый `NotRegistered`.

### Сырьё вызовов не пишется вовсе

Найдено при написании `purge_raw_calls`. Удаление по сроку сделано и покрыто
тестами, но **удалять пока нечего: в `carrier_raw_calls` не пишет ни одна
строка кода.** Проверено поиском по `CarrierRawCall(` — конструктор модели
не вызывается нигде, кроме её объявления.

Цепочка почти собрана: `CarrierHttpClient.request` принимает
`on_raw_call`, клиент СДЭК его пробрасывает — а адаптер не передаёт, потому
что взять его неоткуда. Чтобы домен дал адаптеру приёмник, приёмник должен
попасть в него через `carriers/base.py`: либо полем в DTO `CarrierAccount`,
либо параметром конструктора адаптера. И то и другое — **контракт
`CarrierAdapter`, то есть CLAUDE.md §7, пункт 3**: решение человека.

Пока этого нет:

* разбирать спорную ситуацию с перевозчиком нечем — сырого ответа не осталось;
* `data_quality` в Carrier Score считается без него;
* тридцатидневный срок хранения формально соблюдается тем, что хранить нечего.

Последнее — не повод откладывать: как только сырьё начнёт писаться, удаление
уже будет работать.

## Второй фактор: от заглушки к рабочему входу

Библиотеку выбрал человек — PyOTP (ADR-0018). До этого вход пользователю
с `mfa_enabled` отказывался: проверять код было нечем, а принимать любую
строку из шести символов хуже, чем не пускать.

Что появилось:

* `shared/totp.py` — сверка кода. Возвращает **номер шага**, а не «да/нет»:
  без него защиту от повтора строить не на чем.
* Секрет в `users.mfa_secret` хранится конвертом AES-GCM с привязкой к
  идентификатору пользователя. Открытым текстом одно чтение базы давало бы
  постоянный обход фактора сразу у всех.
* `users.mfa_last_step` (миграция `0011_mfa_replay_guard`) — сожжённый шаг.
  Списание идёт условным `UPDATE ... WHERE mfa_last_step < :step`: два
  одновременных входа с одним подсмотренным кодом попадают в одну строку,
  и выигрывает ровно один. Проверка «прочитали, сравнили, записали»
  на уровне приложения пропустила бы оба.
* `POST /v1/auth/mfa/setup` (секрет и ссылка `otpauth://`, один раз),
  `/enable` и `/disable` — оба требуют код. Все три пишутся в аудит,
  машинному клиенту по API-ключу недоступны.
* Поле кода на форме входа. Видно всем, а не только после отказа: ответ
  на неверный пароль и на отсутствующий код одинаков намеренно.

Тесты: окно ±1 шаг и отказ дальним шагам, мусор вместо кода, чужой секрет,
вход по коду, отказ без кода, отказ на повтор того же кода, отказ коду шага
старше сожжённого, отключение с кодом и без. Часы в этих тестах управляемые:
на настоящих проверка «один шаг принимается один раз» мигала бы на границе
тридцати секунд.

## Разбор исключений: срыв срока был виден только постфактум

Экран `/tracking` из ТЗ v3 (`03-frontend`, раздел 2) в кабинете отсутствовал,
и это скрывало дыру в самой логике. `shipments.is_late` проставляется
в `_settle`, то есть **в момент доставки**. Отправление, у которого срок
из расчёта уже прошёл, а доставки нет, не было помечено ничем: платформа
узнавала о срыве тогда, когда сделать уже нечего, и ровно в том случае,
ради которого дедлайн и задавался.

`GET /v1/tracking/exceptions` собирает едущее, с которым что-то не так,
по трём причинам, и все три выводятся из записанных фактов, а не из настройки:

| Причина | Что означает | Откуда берётся |
|---|---|---|
| `deadline_passed` | Срок из снимка расчёта прошёл, доставки нет | сравнение с `RateQuote.deadline` |
| `problem_status` | Неудачное вручение, возврат, исключение перевозчика | `shared.enums.PROBLEM_STATUSES` — общий набор с уведомлениями тенанту |
| `stalled` | Перевозчик молчит дольше порога опроса | `has_incident` + `incident_type`, порог из `next_poll_after` |

Порог тишины не дублируется: разойдись он с опросом — опрос считал бы
отправление живым ровно тогда, когда экран показывает его зависшим.

Список ограничен `SCAN_LIMIT = 500` едущими отправлениями, и переполнение
видно в ответе (`scanned`, `truncated`) и на экране. Молчаливое усечение
здесь хуже отказа: оператор принял бы неполный список за пустой.

Причин у строки может быть несколько сразу, поэтому сумма счётчиков бывает
больше числа строк — срыв срока и молчание перевозчика разбираются
по-разному. Порядок списка — это порядок работы: сначала тяжесть причины,
внутри неё — кто дольше молчит, и отправление без единого события идёт первым,
а не последним: о нём не известно вообще ничего.

**Чего здесь намеренно нет.** «Риск срыва» как политика — за сколько часов
до срока считать отправление рискованным — не выдуман: это настройка тенанта,
и её никто не принимал. Поэтому в списке только уже наступивший срыв.
Задача `detect_delivery_risk` из расписания по-прежнему не написана
по той же причине, к ней добавляется вопрос, куда уходит её результат.

## Сводка кабинета: всё, кроме экономии

Экран `/dashboard` (P1 в ТЗ) появился, модуль `reports/` перестал быть пустым.
`GET /v1/reports/summary?days=N` считает за окно четыре вещи и все агрегаты —
в базе, а не в Python: выгружать отправления тенанта в память ради одной суммы
значит расти вместе с клиентом и однажды перестать открываться.

* **Соблюдение срока.** Доля «в срок» считается **только по доставкам,
  у которых дедлайн был**. Доставка без срока не может ни уложиться,
  ни опоздать, и в знаменателе она разбавляла бы долю теми, кого никто
  не мерил. Средняя просрочка — по опоздавшим, а не по всем: усреднение
  по всем превращает редкое тяжёлое опоздание в незаметные минуты.
* **Расходы** — по валютам, никогда одной суммой (CLAUDE.md §6). Рядом
  с фактом показано, по скольким отправлениям счёт уже пришёл: без этого
  числа неполный факт выглядит экономией.
* **Отказы от рекомендации** с разбивкой по причинам. Отказ определяется тем,
  какое предложение выбрано, а не флагом в запросе, — иначе метрику можно было
  бы нарисовать со стороны клиента.
* **Открытые исключения** — состояние на сейчас, а не за окно: разбирают то,
  что горит сегодня.

Пустое окно возвращает `null`, а не ноль. Разница дорогая: ноль читается как
«ни одной вовремя», и по такому числу начинают менять перевозчика, тогда как
на деле мерить было нечего.

**Контракт границ модулей поймал транзитивную зависимость.** `reports`
запрещено видеть `carriers`, а сводка берёт счётчики исключений из
`tracking.exceptions`, который брал `PROBLEM_STATES` из `tracking.service`,
а тот импортирует `carriers.base`. Набор проблемных статусов и тип инцидента
«зависло» переехали в `shared.enums`: они нужны трём модулям сразу, и общий
источник тут не украшение — разойдись наборы, экран разбора и уведомление
тенанту говорили бы о разном.

### Экономии в сводке нет намеренно

«Сколько сэкономлено» — главное число продукта и единственное, которое нельзя
посчитать без решения человека. Нужна база сравнения, и от её выбора результат
меняется в разы:

| База | Что получится | Чем плоха |
|---|---|---|
| Самый дорогой вариант выдачи | Самое большое число | Завышает: клиент никогда и не выбрал бы худший вариант |
| Медиана вариантов | Умеренное число | Требует, чтобы вариантов было хотя бы три |
| Тариф перевозчика по умолчанию у тенанта | Ближе всего к правде | Такого поля нет: нужно, чтобы клиент назвал «как возили раньше» |

Это утверждение о деньгах клиента, а не техническая деталь: выбор за человеком,
и до него сводка честно молчит, а не показывает придуманное число.

## Машинный доступ: ключи выпускать было нечем, области не проверялись

Две беды сразу, и вторая пряталась за первой.

`ApiKeyService.issue` и `.revoke` написаны и покрыты тестами с первой недели,
а **HTTP-пути к ним не существовало ни одного**. Аутентификация по `X-Api-Key`
работала и была протестирована — но выпустить ключ снаружи было нельзя,
то есть весь машинный доступ, ради которого она написана, был недостижим.
ТЗ (02-system, раздел 12) называет REST основным внешним интерфейсом,
а 1С — коннектором поверх него.

`api_keys.scopes` заполнялась при выпуске, попадала в `Principal.scopes` —
и **не проверялась нигде**. Ключ «только на расчёт» мог создать и отменить
отправление, то есть потратить деньги клиента у перевозчика. Ревью
безопасности отнесло это к невстроенной функции, и это было верно ровно
до тех пор, пока ключ нельзя было выпустить.

Решение записано в ADR-0019. Главное в нём — **место проверки**: одна таблица
`core.scopes` и один вызов в `current_principal`, а не проверка на каждом
эндпоинте. Проверку, раздаваемую по эндпоинтам, забывают на новом пути,
и забытая проверка не видна ни в тестах, ни в ревью — путь просто работает
шире обещанного. Умолчание — запрет: нового пути в таблице нет, значит ключу
он недоступен.

Кабинетные пути закрыты машинному клиенту целиком — пользователи, ключи,
второй фактор, адресная книга, админка. Смысл в том, чтобы украденный ключ
нельзя было превратить в постоянный доступ: выпустить себе второй ключ,
завести пользователя или снять второй фактор он не может, и отзыв первого
ключа заканчивает историю. На каждый из этих трёх способов есть тест.

**Тест на саму таблицу.** `tests/unit/test_api_scopes.py` требует решения
по каждому пути с субъектом: либо область, либо явная кабинетность. Отдельно
проверяется обход маршрутов — во вложенных роутерах свежего FastAPI путь
маршрута не содержит префикса версии, и наивный обход находил ноль путей,
делая зелёными все проверки файла. Теперь обход сверяется с ответом OpenAPI,
а список путей без аутентификации перечислен поимённо.

### Побочная находка: `GET /v1/auth/me` падал для машинного клиента

Ветка, написанная специально для доступа по ключу, отдавала `500`: подставной
адрес `api-client@aerogram.local` — служебное имя, и `EmailStr` его
не принимает. Вызвать её было некому, пока у ключа не появилось областей
и повода спросить, от чьего имени он ходит. Домен заменён на `example.com`,
зарезервированный IANA для документации, и закрыт тестом.

## Вебхук СДЭК: разбор есть, подтверждать подлинность нечем

Механизм приёма был готов, а принять событие настоящего перевозчика
по-прежнему было нельзя: `parse_webhook` у СДЭК отказывал. Теперь разбирает.

**Источник формата — сторонний.** Официальный SDK покрывает только подписку
на вебхуки (`setWebhooks`, типы `ORDER_STATUS` и `PRINT_FORM`); состава тела
в нём нет вовсе. Форма взята из типов клиента
[`shevernitskiy/cdek`](https://github.com/shevernitskiy/cdek)
(`src/types/api/webhook.ts`). По планке ADR-0010 это на ступень ниже:
источник показывает форму, но подтверждением не является. Сверка добавлена
в список обязательных проверок `tests/fixtures/cdek/README.md`.

**Ловушка, ради которой разбор вынесен в отдельный модуль и покрыт тестами.**
В `attributes` лежат два похожих поля: `status_code` — легаси, число вроде
`"3"`, и `code` — строковый статус (`DELIVERED`, `NOT_DELIVERED`, …), тот
самый словарь, что в `status_map/cdek.yaml`. Взять первое вместо второго —
значит отправлять числа в нормализатор. Он не роняет обработку: помечает
событие несопоставленным и ставит `IN_TRANSIT`. Лента наполняется, доставка
не отмечается никогда, соблюдение срока не считается — и обнаруживается это
на разборе просрочек, а не в тестах. На это есть проверка с двух сторон:
что разбор берёт `code`, и что полученное значение карта статусов знает.

**Подтверждение подлинности — открытый вопрос, и он ваш.** Признаков того,
что СДЭК подписывает вебхуки, нет ни в официальном SDK, ни в сторонних,
ни в описаниях события. Варианты и их цена — в ADR-0015. Коротко: секрет
в URL подписки требует расширения контракта адаптера (`verify_webhook` видит
тело и заголовки, но не строку запроса), список IP ничего не расширяет,
но его надо вести, а принимать без подтверждения нельзя — на этих событиях
считается SLA, и «доставлено» сможет прислать кто угодно.

До решения путь падает закрыто, и отказ теперь называется правильно:
`CarrierNotConfigured` («интеграция не готова, ждать бесполезно»),
а не «перевозчик вернул ошибку» — перевозчик ничего не возвращал.

**С чем сопоставляться, теперь есть.** Заказы СДЭК создаются (неделя 6,
раздел ниже), `external_id` — это `entity.uuid` заказа, тот же идентификатор,
что в поле `uuid` события. Целиком путь заработает после выбора способа
подтверждения подлинности.

## СДЭК, неделя 6: заказ создаётся, ищется, отменяется и отслеживается

До этого у адаптера был реализован только расчёт. `create`, `cancel`,
`find_by_number` и `track` отказывали явно, и весь конвейер после расчёта —
создание → опрос → факт доставки → скор — работал только на поддельном
перевозчике из тестов. Теперь у СДЭК есть все четыре.

Источник — официальный SDK, та же планка, что у расчёта (ADR-0010): сущность
`Order` и её трейты, ответы `EntityResponse` и `OrderResponse`, словарь кодов
ошибок. Фикстуры синтетические и помечены; список сверок при получении
доступов дополнен (`tests/fixtures/cdek/README.md`).

Что важно в реализации:

* **Единицы те же, что в расчёте.** Вес в граммах через ту же `grams_from_kg`,
  габариты в сантиметрах: заказ уходит с тем весом, по которому считали цену.
* **Три идентификатора, и они разные.** `entity.uuid` — заказ в СДЭК, наш
  `external_id`; `cdek_number` — номер накладной, наш `tracking_number`;
  `number` — наш собственный, по нему заказ ищется при сверке «призраков»
  (`GET orders?im_number=`).
* **Накладной в ответе на создание нет.** СДЭК присваивает её позже; результат
  помечается `is_pending`, домен ставит `ACCEPTED` и добирает номер опросом.
* **Отказ приходит телом, а не кодом HTTP.** `requests[0].state == INVALID`
  при статусе 200 — так проверяет SDK, так проверяем и мы. Ради поиска
  HTTP-клиент перевозчиков получил `raise_for_status=False`: «не найден»
  распознаётся по коду `v2_entity_not_found*` в теле, каким бы ни был статус,
  и предохранитель на нём не срабатывает — иначе сверка сотни черновиков
  открыла бы его сама.
* **Направление ошибки на сверке — в дорогую сторону.** `None` только
  на явном «не найден»; любая другая ошибка остаётся ошибкой. Ложное
  «не найден» означает второй заказ у перевозчика — с оплатой и вторым грузом.
* **Страхование** — услуга `INSURANCE` с объявленной стоимостью в рублях;
  копейки превращаются в рубли ровно в одном месте и строкой через `Decimal`.

Не написана печатная форма (неделя 7) — она упирается в ADR-0016.

## Остальные перевозчики: разведка источников проведена, адаптеры ждут решения

«Следующее», пункт 6 — остальные перевозчики поверх существующего СДЭК.
Major Express заблокирован WSDL, который даёт человек. Оставались Деловые
Линии, ПЭК и Яндекс Доставка; по ним проведена разведка источников, потому
что писать адаптер по памяти нельзя, а официальной документации не видно.

**Главный результат: официального SDK нет ни у одного из трёх.** Проверено
по npm, PyPI, Packagist и GitHub. Планка ADR-0010 («сверено с официальным
SDK») к ним неприменима, и это решение человека — см. ADR-0020. Выкачано
и прочитано 42 источника, результат с цитатами —
`docs/integrations/carrier-api-research.md`.

Три находки, которые важнее самих адаптеров:

* **У Яндекса единицы различаются между его собственными контурами.**
  Express — килограммы и метры, Platform (НДД) — граммы и сантиметры, а токен
  один и тот же. Выбор контура — вопрос к человеку: от него зависят единицы,
  формат денег (десятичная строка против копеек) и модель создания заказа.
* **Объёмного веса и делителя нет ни у ПЭК, ни у Деловых Линий.** Обоим
  передаются вес и объём отдельными полями, платный вес считает перевозчик.
  Значит `computes_volumetric_weight = True`, а `carriers.volumetric_divisor`
  для них останется в умолчании и ни на что влиять не будет. Раздел
  «Делитель объёмного веса» выше это уточняет, а не отменяет: делитель
  по-прежнему нужен тем, кто объёмный вес не считает.
* **Отмена не описывается нынешним контрактом адаптера ни у одного из трёх.**
  У Деловых Линий отмены заказа целиком **не существует**: есть асинхронные
  заявки на отмену забора и доставки, с дедлайном 17:00 предыдущего дня
  и результатом `success | in_progress | failed`. У ПЭК две разные отмены
  и окно «не ранее 5–10 минут после подачи». У Яндекса отмена бывает платной,
  и узнать это можно только отдельным вызовом. Наш `CancelResult.accepted` —
  синхронное «да/нет» — не описывает ни одну из трёх ситуаций.

Единицы измерения по всем трём проверены построчным чтением исходников
и процитированы дословно: ошибка здесь не даёт исключения, она даёт цену,
отличающуюся в тысячу раз.

**Что дальше.** Адаптеры не пишутся до ответа по ADR-0020: достаточна ли
сторонняя планка, порядок постройки (предложен ПЭК → ДЛ → Яндекс), контур
Яндекса и что делать с отменой. Разведка при этом не устаревает — при
получении доступов она превращается в список сверок.

## Требует решения человека

0. **Восстановление доступа при потерянном телефоне.**

   Вход по второму фактору работает (PyOTP, ADR-0018): секрет выпускается
   через `POST /v1/auth/mfa/setup`, включается кодом, вход сверяет код и
   не принимает один шаг дважды. Осталась дыра в эксплуатации: потерянный
   телефон означает потерянный вход — владелец не может ни войти, ни отключить
   фактор, потому что и то и другое требует действующего кода.

   **Варианты:** резервные коды (таблица, одноразовость, показ один раз),
   отключение силами администратора платформы с записью в аудит,
   восстановление по почте. У каждого своя цена; выбор — за человеком.

   **Второй открытый вопрос там же:** сделать ли второй фактор обязательным
   для роли `owner` на входе. ТЗ 12.5 называет его обязательным, но сейчас
   его отсутствие — только `log.warning`: запрет одним движением закрыл бы
   вход всем уже заведённым владельцам. Нужен порядок перехода (срок,
   принудительное подключение при первом входе) — и он же зависит
   от восстановления выше.

   **Чего ещё нет в кабинете:** экрана подключения. Секрет и ссылку
   `otpauth://` отдаёт API, но показать QR-код пока некому — подключиться
   можно только вызовом эндпоинта. Поле кода на форме входа есть.

1. **Доступы СДЭК** (`client_id`, `client_secret` в ЛК «Роспломбы»).
   Адаптер написан и покрыт тестами, но на боевом контуре не проверен:
   без доступов нельзя записать реальные фикстуры и сверить единицу
   измерения веса. Список обязательных сверок — в ADR-0010.
2. **Ключ ДаData** — блокирует неделю 3.
3. **VPS и S3 в РФ** — нужны до первого деплоя.
4. **Производственный календарь РФ на 2026 год** — файл
   `backend/src/aerogram/shared/data/production_calendar_ru.yaml` заполнен базовыми
   праздниками ТК РФ, переносы помечены `verified: false`. Без сверки с постановлением
   фактический срок доставки считается приблизительно.
5. **Построчное ревью миграций и RLS** — требование CLAUDE.md §7. Файлы:
   `alembic/versions/20260829_0001_initial_schema.py`,
   `20260829_0002_tenant_isolation.py`, `20260829_0003_app_role_grants.py`,
   `20260829_0004_directories_week3.py`.
6. **ADR-0004** (окно поиска пользователя при входе) — осознанный компромисс,
   требует подтверждения.
7. **Источник тарифа ПЭК не укладывается в контракт.** Схема `RateOffer.source`
   в `openapi.yaml` имеет ровно два значения — `client_contract` и `logistics_os`.
   Но бэкенд-ТЗ, раздел 11, требует для ПЭК «separate public vs contract source
   explicitly»: публичный расчёт ПЭК не является ни договором клиента, ни
   тарифом платформы. Сейчас такой источник даёт `NULL`, а не выдумку.
   Варианты: считать публичный расчёт разновидностью `logistics_os`, либо
   добавить в контракт третье значение. Решать до написания адаптера ПЭК.

8. **Преобразование цены в `price_index` (Carrier Score).** Раздел 10.1
   требует «нормированное положение цены относительно медианы, обрезанное
   в [0; 1]», но точного вида не задаёт. Выбрано так: ровно по медиане —
   половина шкалы, вдвое дешевле — единица, вдвое дороже — ноль. Центр
   в 0.5, а не в 1, потому что иначе все, кто дешевле медианы, получали бы
   одинаковый максимум и переставали различаться. Требует подтверждения
   вместе с весами формулы: изменение вида обязано менять `FORMULA_VERSION`.

9. **Веса «оптимального» выбора** (`routing/strategies.py`, `OPTIMAL_WEIGHTS`).
   Сейчас цена 0.40, срок 0.30, надёжность 0.20, риск 0.10 — рабочее начальное
   приближение, а не обоснованная бизнесом величина. CLAUDE.md §7, пункт 8:
   формула рекомендации требует решения человека. Пересмотр весов обязан
   менять `ALGORITHM_VERSION`, иначе исторические рекомендации станут
   несопоставимыми.

10. **Язык условий и действий правил маршрутизации.** Таблица `routing_rules`
   создана, `conditions` и `actions` — JSONB, но ТЗ v3 не определяет их состав.
   Сочинять язык правил без спецификации я не стал: сейчас правила влияют
   только на `policy_version` в снимке рекомендации. Нужен состав условий
   (перевозчик, направление, вес, стоимость груза) и действий (запретить,
   разрешить, порог страхования, автовыбор).

11. **`tenant_id` без внешнего ключа на `tenants`.** Все 16 таблиц из миграции
   0001 имеют индекс по `tenant_id`, но не имеют FK. Новые таблицы Decision
   Engine сделаны так же — ради единообразия схемы, а не потому, что так лучше.
   FK защитил бы от строк-сирот; добавление его — миграция на 21 таблицу
   и решение уровня CLAUDE.md §7.

12. **Отправления: три расхождения с контрактом.**

    *Отмены в контракте нет.* FR-2.6 её требует, в `openapi.yaml` пути нет.
    Реализована как `POST /v1/shipments/{id}/cancel` и объявлена служебной
    в тесте соответствия. Нужно либо дополнить контракт, либо отказаться
    от требования; молча не делать — худший вариант, без отмены заказ
    у перевозчика живёт своей жизнью.

    *Словарь статусов беднее нашего.* ТЗ, раздел 9, требует четырнадцати
    состояний, схема `Shipment` перечисляет десять. Перевод на границе API
    идёт с потерями: «возврат» и «неудачная попытка вручения» превращаются
    в `Exception`, хотя это разные события с разными последствиями
    для клиента. Внутри они по-прежнему различимы.

    *`external_id` означает в контракте две разные вещи.* В `Shipment` это
    идентификатор заказа у перевозчика (бэкенд-ТЗ, раздел 5), а в
    `CreateShipmentRequest` клиент прислать его не может — заказа ещё нет.
    Принято читать его как номер клиента в его системе: если он задан,
    он становится номером отправления. Ответ при этом отдаёт в том же поле
    идентификатор ТК. Одно имя для двух смыслов рано или поздно укусит.

13. **Построчное ревью создания отправления** — требование CLAUDE.md §7,
    пункт 4 (идемпотентность и сверка «призраков»). Решения, принятые мной
    и требующие подтверждения: черновик пишется отдельной транзакцией
    (второе соединение на время создания); номер выводится из ключа
    идемпотентности, а не выдаётся случайно; повтор с тем же ключом
    и другим телом сверяется по полям строки, а не по хешу тела —
    отдельной колонки под отпечаток нет.

14. **Два поля рекомендации расходятся со схемой контракта**, и оба
    расхождения идут от прозы того же ТЗ. `confidence` в схеме
    `Recommendation` отсутствует, но системное ТЗ, раздел 9, требует явно
    показывать низкую уверенность, а фронт-ТЗ, раздел 4, помещает её
    в карточку. `recommended_offer_id` в схеме обязателен и не допускает
    null, но когда в срок не укладывается никто, рекомендации нет.
    Нужно либо дополнить контракт, либо изменить требование.

15. **Лицензия справочника городов** — вынесена в раздел «Перед выпуском MVP»
   ниже. Продукт работает без неё: `cities` наполняется лениво из подсказок
   ДаData, механизм реализован и покрыт тестами.

## Перед выпуском MVP

Список того, что обязано быть закрыто до боевого запуска. В отличие от
задач разработки, здесь почти всё требует решения человека, а не кода,
и почти всё дешевле закрыть заранее, чем задним числом.

### 1. Лицензия справочника городов — РЕШИТЬ ДО ЗАПУСКА

Официальный справочник городов ДаData `github.com/hflabs/city` (1117 городов,
ровно те поля, что нужны модели `City`) распространяется под
**CC-BY-SA 4.0**. Лицензия требует указания авторства и распространяет
условие share-alike на производные базы данных. Что это означает для
коммерческого SaaS с закрытым кодом — вопрос к юристу, а не к разработчику.

Соседний датасет `hflabs/settlement-fias-guid` (160 тыс. населённых пунктов)
использовать **нельзя вовсе**: его лицензия прямо запрещает коммерческое
применение.

Варианты:

| Вариант | Что даёт | Чего стоит |
|---|---|---|
| Юридическая оценка CC-BY-SA и включение справочника | Мгновенный старт: 1117 городов в базе с первого дня, подсказки работают без ДаData | Консультация юриста; возможное требование раскрыть производную базу |
| Ленивое наполнение из ДаData (**реализовано сейчас**) | Никаких правовых вопросов; города появляются по факту обращения | Первые обращения к новому городу требуют доступности ДаData; локальные подсказки на старте пусты |
| Выгрузка ГАР/ФИАС с сайта ФНС | Первоисточник, свободные условия | Объём в десятки гигабайт и своя загрузка — недели работы |

**Текущее состояние: выбран второй вариант**, продукт работает без справочника.
Решение нужно принять до момента, когда лимит ДаData станет узким местом.

### 2. Производственный календарь РФ на 2026 год

`backend/src/aerogram/shared/data/production_calendar_ru.yaml` заполнен базовыми
нерабочими днями по ТК РФ, переносы помечены `verified: false`. Без сверки
с постановлением Правительства фактический срок доставки считается
приблизительно, а через него — Carrier Score.

### 3. Юридический пакет по персональным данным

Раздел 12.2 ТЗ: уведомление в Роскомнадзор об обработке ПДн, политика
обработки, согласия и поручения на обработку в договоре с тенантом.
Готовится параллельно разработке, к запуску обязан быть.

### 4. Внешнее тестирование на проникновение

Раздел 12.9 ТЗ: перед промышленным запуском. Отдельно проверить публичную

### 5. Проверка восстановления из бэкапа
