# Доступы перевозчиков (договор клиента)

Платформа работает **по договорам клиента**: у каждого тенанта свои условия
и свои доступы к личному кабинету перевозчика. Отсюда следует главное правило.

> Учётные данные перевозчика не лежат ни в репозитории, ни в переменных
> окружения. Они хранятся зашифрованными в `carrier_accounts.credentials_encrypted`
> отдельно для каждого тенанта.

В переменных окружения задаются только адреса сервисов — то, что одинаково
для всех клиентов.

## Где что указывается

| Что | Где | Попадает в git |
|---|---|---|
| Логин, пароль, ключ API, секрет | `carrier_accounts.credentials_encrypted`, шифрование AES-256-GCM | нет |
| Адрес веб-сервиса, если он не из WSDL | переменная окружения, см. `.env.example` | нет (значение), да (имя переменной) |
| WSDL, описания протоколов, фикстуры | репозиторий, рядом с адаптером | да |
| Ключи шифрования (`CREDENTIAL_KEYS`) | переменная окружения | нет |

Шифротекст привязан к идентификатору строки: скопировать его в чужую учётную
запись бесполезно — он там не расшифруется.

## Состав полей

Одного набора на всех не существует, поэтому хранилище — свободный словарь,
а состав объявлен для каждого перевозчика в
`backend/src/aerogram/carriers/credentials.py`.

| Перевозчик | Поля | Где взять |
|---|---|---|
| Major Express | `login`, `password` (Basic Auth) | менеджер Major Express вместе с доступом к веб-сервису |
| СДЭК | `client_id`, `client_secret` (OAuth) | личный кабинет СДЭК, раздел интеграции |
| Деловые Линии | не определены | появятся вместе с адаптером |
| ПЭК | не определены | появятся вместе с адаптером |
| Яндекс Доставка | не определены | появятся вместе с адаптером |

Состав полей для трёх последних сознательно **не выдуман**: способ авторизации
у них не прочитан ни по коду, ни по документации — домены перевозчиков закрыты
сетевой политикой окружения разработки. Назвать поле раньше, чем известен
протокол, значит попросить у клиента не то и потом просить заново. До появления
адаптера доступы этих ТК заводятся с явным перечислением полей (см. ниже).

## Как завести

Экрана в кабинете пока нет, поэтому — скрипт. Значения он читает с ввода,
а не из аргументов командной строки: аргументы видны в `ps` и остаются
в истории оболочки.

Интерактивно (ввод не отображается):

```bash
cd backend
uv run python scripts/set_carrier_credentials.py --tenant <uuid-тенанта> --carrier major
```

Неинтерактивно — из файла с правами `600`, который удаляется сразу после:

```bash
umask 077 && printf '{"login":"...","password":"..."}' > creds.json
uv run python scripts/set_carrier_credentials.py --tenant <uuid> --carrier major < creds.json
shred -u creds.json
```

Перевозчик, чей состав полей ещё не объявлен:

```bash
uv run python scripts/set_carrier_credentials.py --tenant <uuid> --carrier pecom --fields api_key
```

Режим договора задаётся `--mode`: `own_contract` (по умолчанию — договор
клиента) или `aerogram` (тариф платформы).

Скрипт печатает только **имена** записанных полей. Значения не попадают
ни в вывод, ни в логи: `shared.logging.mask_pd` и правило «учётные данные
перевозчика не попадают в ответ, лог и снимок никогда» (CLAUDE.md §6).

## Проверка

После записи учётная запись получает статус `unchecked`: прежний вердикт
проверки к новым данным не относится. Расчёт по этому перевозчику покажет
результат — либо предложения, либо строку `failures` с внятной причиной:

* `carrier_auth_error` — перевозчик отклонил доступы, проверьте значения;
* `carrier_not_configured` — интеграция не готова: не заполнены поля или
  не хватает описания протокола. Повторять бесполезно, нужны действия
  администратора;
* `carrier_unavailable` — до перевозчика не достучались, имеет смысл повторить.
