## 1. Продукт

### 1.1. Назначение

**Aerogram Logistic OS** — облачная мультитенантная платформа, которая становится единым слоем между информационными системами компании-грузоотправителя и транспортными компаниями.

```
Клиент (веб-кабинет / API / ERP)
            ↓
   Aerogram Logistic OS
   расчёт · выбор · создание · трекинг · документы · аналитика
            ↓
СДЭК · Major Express · Деловые Линии · [+ Почта России, Boxberry, ПЭК — очередь 2]
```

Позиционирование в одну фразу:

> Единая система управления всеми перевозчиками компании, которая автоматически выбирает оптимальный способ доставки по цене, сроку и риску.

Платформа принципиально **не является агрегатором-перепродавцом**. Клиент подключает свои действующие договоры с перевозчиками и работает по своим ставкам; параллельно доступны ставки Aerogram там, где они выгоднее. Обе цены показываются в одной выдаче.

### 1.2. Проблема, которую решает MVP

Компания с 3–8 перевозчиками сегодня работает так: отдельный личный кабинет у каждого ТК, ручной перенос данных, расчёт стоимости по трём вкладкам браузера, трекинг по трём сайтам, отсутствие сводной статистики по срокам и качеству. Решение о выборе перевозчика принимается по привычке или по цене, без учёта риска срыва срока.

### 1.3. Границы MVP

**Входит (7 функций):**

| № | Функция | Краткое описание |
|---|---|---|
| F1 | Единый расчёт стоимости и срока | Один запрос → котировки от всех подключённых ТК |
| F2 | Создание отправления | Формирование заказа/накладной в системе выбранного ТК |
| F3 | Единый трекинг | Нормализованная лента статусов по всем ТК |
| F4 | Печать документов | Этикетки и накладные ТК + сводные формы Aerogram |
| F5 | Сравнение перевозчиков | Таблица выдачи: цена, срок, SLA, риск, скор |
| F6 | План против факта | Заявленный срок vs фактический, накопление статистики |
| F7 | Carrier Score | Собственный рейтинг качества перевозчиков |

**Не входит в MVP (зафиксировано явно):**

- Обмен с 1С и любыми учётными системами (перенесено в очередь 2)
- Биллинг, взаиморасчёты, начисление логистической маржи, счета клиентам
- Возвраты и обратная логистика
- Претензионный модуль (в MVP только ручной флаг инцидента)
- Cargo Control (ШокЛог / IoT-метки удара, наклона, температуры) — очередь 2
- Сборные грузы, авиа/авто-фрахт, международная доставка, море и ж/д
- Мобильные приложения
- Складские остатки, WMS-функции, комплектация
- ML-модель выбора перевозчика (в MVP — детерминированная формула скора)

### 1.4. Целевой пользователь MVP

Приоритет — **B2B-отправитель**: производственная, торговая или сервисная компания, отправляющая от 30 до 3 000 отправлений в месяц, с высокой ценностью груза и жёсткими сроками. Вторично поддерживается **e-commerce**-сценарий (массовая отправка мелких посылок) — через пакетную загрузку и API, без отдельного UI.

Практическое следствие для архитектуры: расчёт и создание должны работать и поштучно (человек в кабинете), и пакетно (API/файл до 1 000 строк за операцию).

### 1.5. Метрики успеха MVP

| Метрика | Целевое значение к концу пилота (90 дней после запуска) |
|---|---|
| Подключённых компаний-клиентов | ≥ 5 |
| Отправлений, проведённых через систему | ≥ 3 000 |
| Доля отправлений с полной лентой трекинга | ≥ 95 % |
| Время от входа в систему до создания отправления (кабинет, повторный отправитель) | ≤ 90 секунд |
| Доля расчётов, где выдача получена от всех подключённых ТК | ≥ 90 % |
| Доля отправлений, где Carrier Score имел достаточную выборку | ≥ 60 % к концу пилота |

### 1.6. Термины

| Термин | Определение |
|---|---|
| Тенант (tenant) | Компания-клиент платформы. Полная изоляция данных |
| Перевозчик (carrier) | Транспортная компания, подключённая через адаптер |
| Адаптер (CarrierAdapter) | Модуль, приводящий API конкретного ТК к единому внутреннему контракту |
| Котировка (quote) | Одно предложение одного ТК по одному тарифу: цена + срок |
| Выдача (rate shopping result) | Набор котировок по одному запросу расчёта |
| Отправление (shipment) | Сущность Aerogram, соответствующая одному заказу/накладной у ТК |
| Учётная запись перевозчика (carrier_account) | Пара «тенант × перевозчик» с реквизитами доступа и режимом договора |
| Плановый срок | Срок доставки, заявленный ТК в момент расчёта |
| Фактический срок | Разница между приёмом груза и финальным статусом «доставлено», в рабочих днях |
| Carrier Score | Интегральная оценка перевозчика 0–100 в заданном разрезе |

### 2.1. Роли внутри тенанта

| Роль | Права |

| Роль | Права |
|---|---|
| `platform_admin` | Управление тенантами, адаптерами, справочниками, весами скора |

## 3. Ключевые сценарии

### С-1. Разовая отправка через кабинет (основной B2B-сценарий)

1. Логист открывает «Новое отправление».
2. Вводит откуда/куда (адрес или город + терминал/ПВЗ), габариты, вес, объявленную ценность, тип груза, требуемую дату доставки.
3. Нажимает «Рассчитать». Система параллельно опрашивает подключённые ТК.
4. Через ≤ 4 секунд появляется таблица сравнения: перевозчик, тариф, цена, срок, дата доставки, Carrier Score, метка «уложится в срок / риск».
5. Логист выбирает строку → «Создать отправление».
6. Система создаёт заказ у ТК, получает трек-номер и этикетку, ставит отправление в мониторинг.
7. Печатается этикетка. Отправление появляется в общем списке.

### С-2. Пакетная отправка (e-commerce)

Загрузка CSV/XLSX до 1 000 строк → валидация → массовый расчёт по правилу выбора (минимальная цена / максимальный скор / уложиться в срок) → массовое создание → один PDF со всеми этикетками + реестр приёма-передачи.

### С-3. Создание отправления из внешней системы через API

`POST /v1/rates` → `POST /v1/shipments` с указанием `rate_id` → получение `tracking_number` и ссылки на этикетку → подписка на вебхуки статусов.

### С-4. Контроль срока

Ежедневно в 08:00 система формирует список отправлений с риском срыва: плановая дата доставки ≤ сегодня + 1 день, а фактический статус не соответствует ожидаемому этапу маршрута. Список выводится на дашборд и уходит уведомлением.

### С-5. Разбор качества перевозчика

Логист открывает отчёт «План vs факт» за период, фильтрует по направлению и весовой категории, видит: среднее отклонение в днях, долю просрочек, динамику скора помесячно.

## 4. Архитектура

### 4.1. Состав системы

| Компонент | Назначение |
|---|---|
| `web-app` | SPA-кабинет, React + TypeScript |
| `api-gateway` | Публичное REST API, аутентификация, rate limiting, версионирование |
| `core-service` | Домен: тенанты, отправления, адреса, справочники, права |
| `rating-service` | Rate shopping: параллельный опрос адаптеров, кэш, ранжирование |
| `carrier-adapters` | По одному модулю на ТК, единый интерфейс |
| `tracking-service` | Опрос статусов, приём вебхуков ТК, нормализация, лента событий |
| `document-service` | Получение и генерация печатных форм, хранение в S3 |
| `score-service` | Расчёт Carrier Score по расписанию, витрины аналитики |
| `worker` | Celery: фоновые задачи, ретраи, расписания |
| `postgres` | Основное хранилище |
| `redis` | Кэш котировок, брокер очередей, идемпотентность |
| `s3` | Этикетки, накладные, отчёты, загруженные файлы |

### 4.2. Контракт адаптера перевозчика

Каждый адаптер реализует интерфейс. Ядро не знает ничего о специфике конкретного ТК.

```python
class CarrierAdapter(Protocol):
    code: str                    # "cdek", "major", "dellin"
    capabilities: Capabilities   # что реально поддерживается

    async def quote(self, req: QuoteRequest,
                    acc: CarrierAccount) -> list[Quote]: ...
    async def create(self, req: ShipmentRequest,
                     acc: CarrierAccount) -> ShipmentResult: ...
    async def label(self, ext_id: str, fmt: LabelFormat,
                    acc: CarrierAccount) -> bytes: ...
    async def track(self, ext_id: str,
                    acc: CarrierAccount) -> list[RawEvent]: ...
    async def cancel(self, ext_id: str,
                     acc: CarrierAccount) -> CancelResult: ...
    async def sync_refs(self, acc: CarrierAccount) -> RefSyncReport: ...
    def parse_webhook(self, payload: dict) -> list[RawEvent]: ...
```

`Capabilities` — булев набор: `supports_webhooks`, `supports_pickup_request`, `supports_zpl`, `supports_cod`, `supports_insurance`, `supports_cancel`, `max_places`, `supported_label_formats`. Интерфейс не должен деградировать до «наименьшего общего знаменателя»: если ТК умеет больше, это доступно через `carrier_extras` — типизированный JSON-блок в запросе и ответе.

**Требование:** добавление нового перевозчика не должно требовать изменений в `core-service`, `web-app` или публичном API. Только новый модуль адаптера + запись в справочнике.

### 4.4. Мультитенантность

Модель: **общая база, общая схема, обязательная колонка `tenant_id`** во всех бизнес-таблицах.

Требования:
- Изоляция обеспечивается на уровне PostgreSQL Row Level Security, а не только кодом приложения.
- Любой запрос выполняется в транзакции с установленным `SET LOCAL app.tenant_id`.
- Запрещены запросы к бизнес-таблицам без предиката по тенанту; проверяется автотестом на уровне репозиториев.
- Ключи доступа к ТК хранятся зашифрованными (AES-GCM, ключ в KMS/переменных окружения, ротация раз в год).

## 5. Модель данных

Ниже — обязательный минимум. Технические поля (`id`, `created_at`, `updated_at`, `tenant_id`) подразумеваются везде, кроме платформенных справочников.

### 5.1. Ядро

**`tenants`** — `name`, `inn`, `kpp`, `legal_address`, `status` (`trial`/`active`/`suspended`), `plan`, `timezone`.

**`users`** — `tenant_id`, `email`, `password_hash`, `full_name`, `role`, `is_active`, `last_login_at`, `mfa_secret`.

**`api_keys`** — `tenant_id`, `name`, `key_hash`, `scopes[]`, `last_used_at`, `expires_at`, `revoked_at`.

**`counterparties`** — контрагенты тенанта (отправители и получатели): `type` (`legal`/`individual`/`entrepreneur`), `name`, `inn`, `kpp`, `contact_person`, `phone`, `email`.

**`addresses`** — `counterparty_id`, `label`, `country_code`, `region`, `city`, `city_fias_id`, `postal_code`, `street`, `house`, `flat`, `lat`, `lon`, `is_default_sender`, `comment`.

**Требование:** города нормализуются по ФИАС и хранят кросс-таблицу кодов ТК (`city_carrier_map`: `city_fias_id`, `carrier_code`, `carrier_city_code`). Это критично: сопоставление городов — источник большинства ошибок в мультиперевозочных системах.

### 5.2. Перевозчики

**`carriers`** (платформенный справочник) — `code`, `name`, `logo_url`, `is_active`, `capabilities` (JSONB).

**`carrier_accounts`** — `tenant_id`, `carrier_id`, `mode` (`own_contract` — договор клиента / `aerogram` — договор платформы), `credentials_encrypted`, `contract_number`, `is_sandbox`, `status`, `last_check_at`.

**`carrier_services`** — `carrier_id`, `code`, `name`, `mode` (`door_door`, `door_terminal`, `terminal_door`, `terminal_terminal`), `is_express`.

**`carrier_terminals`** — `carrier_id`, `external_code`, `city_fias_id`, `address`, `type` (`pvz`/`terminal`/`postamat`), `work_hours`, `lat`, `lon`, `has_cash`, `has_card`, `max_weight`, `synced_at`.

### 5.3. Расчёт

**`rate_requests`** — `tenant_id`, `user_id`, `payload` (JSONB нормализованного запроса), `hash` (для кэша), `created_at`, `duration_ms`.

**`rate_quotes`** — `rate_request_id`, `carrier_id`, `carrier_account_id`, `service_code`, `tariff_code`, `price`, `currency`, `price_source` (`own_contract`/`aerogram`/`public`), `transit_days_min`, `transit_days_max`, `promised_delivery_date`, `score_at_quote`, `rank`, `raw_response` (JSONB), `error_code`, `expires_at`.

Котировка живёт 15 минут. При создании отправления по истёкшей котировке система обязана пересчитать и, если цена изменилась более чем на порог (по умолчанию 5 %), потребовать явного подтверждения.

### 5.4. Отправления

**`shipments`** — `tenant_id`, `number` (внутренний), `carrier_id`, `carrier_account_id`, `external_id`, `tracking_number`, `service_code`, `tariff_code`, `status` (нормализованный), `carrier_status_raw`, `sender_address_id`, `recipient_address_id`, `declared_value`, `payment_type`, `price_quoted`, `price_actual`, `promised_delivery_date`, `actual_delivery_date`, `transit_days_planned`, `transit_days_actual`, `is_late`, `delay_days`, `has_incident`, `incident_type`, `created_via` (`web`/`api`/`import`), `rate_quote_id`, `cancelled_at`, `comment`.

**`shipment_places`** — `shipment_id`, `number`, `weight_kg`, `length_cm`, `width_cm`, `height_cm`, `volume_weight_kg`, `barcode`.

**`shipment_items`** — товарное наполнение (для описи и объявленной ценности): `name`, `quantity`, `price`, `weight`, `nds_rate`, `marking_code`.

**`shipment_events`** — `shipment_id`, `occurred_at`, `received_at`, `status_normalized`, `status_raw`, `city`, `comment`, `source` (`api_poll`/`webhook`/`manual`/`sensor`), `raw` (JSONB).

> **Проектное решение:** поле `source` со значением `sensor` закладывается уже в MVP, хотя модуль Cargo Control в MVP не разрабатывается. Это позволит во второй очереди писать события датчиков удара, наклона и температуры в ту же ленту, что и статусы перевозчика, без миграции схемы.

**`documents`** — `shipment_id`, `type` (`label`/`waybill`/`manifest`/`inventory`/`acceptance_register`), `format` (`pdf`/`zpl`/`png`), `s3_key`, `page_count`, `generated_at`.

### 5.5. Аналитика и скор

**`carrier_score_snapshots`** — `carrier_id`, `scope_type` (`global`/`direction`/`direction_weight`), `scope_key`, `period_start`, `period_end`, `sample_size`, `on_time_rate`, `avg_delay_days`, `incident_rate`, `price_index`, `data_quality`, `score`, `confidence` (`high`/`medium`/`low`/`insufficient`), `formula_version`, `calculated_at`.

**`audit_log`** — `tenant_id`, `actor_user_id`, `action`, `entity_type`, `entity_id`, `ip`, `user_agent`, `payload_diff` (JSONB), `created_at`.

## 6. Функциональные требования

Нумерация сквозная. Каждое требование должно иметь тест.

### FR-1. Единый расчёт стоимости и срока

**FR-1.1.** Форма расчёта принимает: адрес или город отправления и назначения (в т. ч. выбор терминала/ПВЗ), список мест с габаритами и весом, объявленную ценность, тип груза (документы / посылка / груз / оборудование), опции (страхование, забор от адреса, доставка до адреса, наложенный платёж, доставка в выходной), желаемую дату забора и требуемую дату доставки.

**FR-1.2.** Объёмный вес рассчитывается по формуле `Д × Ш × В (см) / делитель`, делитель настраивается на уровне перевозчика (по умолчанию 5000). В расчёте участвует максимум из фактического и объёмного веса — если ТК не считает это сам.

**FR-1.3.** Система опрашивает все активные `carrier_accounts` тенанта **параллельно**. Таймаут на одного перевозчика — 3 секунды (конфигурируемо), общий дедлайн ответа — 5 секунд.

**FR-1.4.** Перевозчик, не ответивший в срок или вернувший ошибку, показывается отдельной строкой со статусом ошибки и человекочитаемой причиной. Ошибка одного ТК не должна ронять выдачу.

**FR-1.5.** Если у тенанта для перевозчика заданы оба режима (`own_contract` и `aerogram`), возвращаются обе котировки, помеченные источником цены. Если ставка Aerogram ниже собственной — строка визуально выделяется с указанием экономии в рублях и процентах.

**FR-1.6.** Результаты кэшируются в Redis по хешу нормализованного запроса на 15 минут. Кэш инвалидируется при изменении учётной записи ТК или тарифных настроек.

**FR-1.7.** Каждый запрос и каждая котировка сохраняются в БД, включая сырой ответ ТК. Это исходные данные для скора и для разбора спорных ситуаций.

**FR-1.8.** Пакетный расчёт: `POST /v1/rates/batch` до 1 000 строк, выполняется асинхронно, возвращает `job_id`, результат забирается по `GET /v1/jobs/{id}`.

### FR-2. Создание отправления

**FR-2.1.** Создание возможно двумя путями: по `rate_id` из выдачи (основной) или прямым указанием `carrier_code` + `service_code` (для интеграций, где расчёт не нужен).

**FR-2.2.** Перед отправкой в ТК выполняется валидация: обязательные поля по правилам конкретного ТК (берутся из адаптера), лимиты по весу и габаритам, поддержка направления, корректность телефонов и ИНН.

**FR-2.3.** Операция идемпотентна. Клиент передаёт заголовок `Idempotency-Key`; повторный запрос с тем же ключом в течение 24 часов возвращает первоначальный результат, а не создаёт дубль. Ключ хранится в Redis.

**FR-2.4.** Ответ содержит: внутренний номер, трек-номер ТК, ссылку на этикетку, плановую дату доставки, фактическую цену (если ТК возвращает её при создании).

**FR-2.5.** Если ТК создал заказ, но ответ не дошёл (таймаут, разрыв), система обязана выполнить сверку: фоновая задача запрашивает у ТК заказ по внутреннему номеру и досоздаёт запись. Отправления-«призраки» недопустимы.

**FR-2.6.** Отмена отправления доступна, пока ТК её принимает (`capabilities.supports_cancel`). Статус переводится в `CANCELLED`, событие пишется в ленту.

**FR-2.7.** Пакетное создание из файла: поддерживаются CSV и XLSX, шаблон скачивается из интерфейса, ошибки валидации возвращаются построчно с указанием поля.

### FR-3. Единый трекинг

**FR-3.1.** Для перевозчиков с вебхуками (`supports_webhooks`) статусы принимаются push-моделью на `POST /v1/webhooks/{carrier_code}` с проверкой подписи/секрета.

**FR-3.2.** Для остальных — polling по расписанию с адаптивной частотой:

| Состояние отправления | Частота опроса |
|---|---|
| Создано, груз не забран | каждые 60 мин |
| В пути | каждые 3 часа |
| В городе назначения / на доставке | каждые 30 мин |
| Финальный статус | опрос прекращается |
| Нет событий > 5 суток | 1 раз в сутки, флаг «зависшее» |

**FR-3.3.** Все статусы приводятся к единой модели (раздел 9). Сырой статус сохраняется всегда.

**FR-3.4.** Лента событий отправления отображается единообразно независимо от ТК: дата, время, город, статус, комментарий.

**FR-3.5.** Публичная страница трекинга по трек-номеру, без авторизации, с ограничением по частоте запросов. Не раскрывает цену, контрагентов и внутренние номера.

**FR-3.6.** Вебхуки наружу: тенант подписывается на события `shipment.status_changed`, `shipment.delivered`, `shipment.exception`, `shipment.delayed`. Доставка с ретраями (5 попыток, экспоненциальная задержка), подпись HMAC-SHA256 в заголовке.

### FR-4. Печать документов

**FR-4.1.** Этикетка запрашивается у ТК в его формате. Поддерживаются PDF (A4, A5, 100×150) и ZPL, если ТК их отдаёт.

**FR-4.2.** Пакетная печать: объединение этикеток по выбранным отправлениям в один PDF, порядок — как в списке.

**FR-4.3.** Собственные формы Aerogram, генерируемые системой:
- **Реестр приёма-передачи** — список отправлений, передаваемых курьеру ТК за день, с полями для подписи и штампа.
- **Опись вложения** — по позициям `shipment_items`.
- **Манифест** — если ТК требует и поддерживает.

**FR-4.4.** Все сгенерированные документы сохраняются в S3 и доступны повторно без обращения к ТК. Ссылка подписанная, время жизни — 24 часа.

**FR-4.5.** Если ТК отдаёт этикетку асинхронно (сначала запрос на формирование, потом получение файла), адаптер обязан скрыть эту асинхронность: клиенту возвращается ссылка, которая станет валидной после готовности, а UI показывает состояние «готовится».

### FR-5. Сравнение перевозчиков

**FR-5.1.** Выдача — таблица со столбцами: перевозчик, тариф/услуга, цена, источник цены, срок в днях, плановая дата доставки, Carrier Score, доверие к скору, метка соответствия требуемому сроку.

**FR-5.2.** Сортировка по любому столбцу. Пресеты: «дешевле», «быстрее», «надёжнее» (по скору), «оптимально» (комбинированный ранг).

**FR-5.3.** Комбинированный ранг по умолчанию: нормализованная цена (вес 0,4) + нормализованный срок (0,3) + скор (0,3). Веса настраиваются на уровне тенанта.

**FR-5.4.** Если задана требуемая дата доставки, строки, не укладывающиеся в неё, помечаются и по умолчанию уходят вниз выдачи, но не скрываются.

**FR-5.5.** Правила автовыбора для пакетных сценариев и API: `cheapest`, `fastest`, `best_score`, `best_value`, `cheapest_meeting_deadline`. Правило может быть закреплено за тенантом как политика по умолчанию.

**FR-5.6.** Для каждой строки доступна расшифровка: из чего сложилась цена (если ТК возвращает составляющие) и из чего сложился скор.

### FR-6. Плановый срок против фактического

**FR-6.1.** Плановый срок фиксируется в момент расчёта из ответа ТК и не пересчитывается задним числом. Источник — только API перевозчика, не публичные таблицы сроков на сайтах.

**FR-6.2.** Фактический срок = количество **рабочих** дней между событием фактического приёма груза (`PICKED_UP` / `ACCEPTED`) и финальным `DELIVERED`. Календарь — производственный календарь РФ, справочник обновляется ежегодно, учитываются переносы.

**FR-6.3.** Отправление помечается `is_late = true`, если `actual_delivery_date > promised_delivery_date`. Величина в днях пишется в `delay_days`.

**FR-6.4.** Отчёт «План vs факт»: фильтры по периоду, перевозчику, направлению (регион → регион), весовой категории, типу груза. Показатели: количество, доля в срок, среднее и медианное отклонение, 90-й перцентиль срока, доля инцидентов.

**FR-6.5.** Экспорт отчёта в XLSX и CSV.

**FR-6.6.** Из отчёта строится динамика по месяцам — деградацию качества перевозчика нужно видеть до того, как она станет проблемой.

### FR-7. Carrier Score

Методика вынесена в раздел 10. Функциональные требования:

**FR-7.1.** Скор считается фоновой задачей ежесуточно и при накоплении каждых 50 новых финализированных отправлений.

**FR-7.2.** Скор считается в трёх разрезах с приоритетом от узкого к широкому: `direction_weight` (пара регионов × весовая категория) → `direction` (пара регионов) → `global` (весь перевозчик).

**FR-7.3.** При недостаточной выборке система **обязана** показать статус доверия, а не подставить глобальное значение молча. Значения: `high` (≥ 100 наблюдений), `medium` (30–99), `low` (10–29), `insufficient` (< 10 — скор не показывается, выводится «недостаточно данных»).

**FR-7.4.** Формула и веса хранятся в конфигурации, версионируются (`formula_version`), изменение весов не переписывает историю снапшотов.

**FR-7.5.** В интерфейсе доступна расшифровка скора по компонентам с указанием размера выборки и периода.

**FR-7.6.** Скор, действовавший в момент выдачи, сохраняется в `rate_quotes.score_at_quote` — чтобы можно было ретроспективно оценить качество рекомендаций.

### FR-8. Справочники и нормализация адресов

**FR-8.1.** Города и адреса нормализуются через ФИАС/ДаData. Хранится `city_fias_id` как единый ключ.

**FR-8.2.** Таблица соответствия `city_carrier_map` заполняется при синхронизации справочников каждого ТК; несопоставленные города попадают в очередь ручного сопоставления в админке платформы.

**FR-8.3.** Справочники терминалов и ПВЗ синхронизируются ежесуточно.

**FR-8.4.** Адресная книга тенанта: сохранённые отправители и получатели, поиск по названию и ИНН, автоподстановка.

### FR-9. Тарифы по договору клиента

**FR-9.1.** Режим `own_contract`: система использует учётные данные клиента при обращении к API ТК, поэтому получает цены с персональными скидками автоматически. Это основной способ.

**FR-9.2.** Резервный способ для ТК, чей API не отдаёт персональные цены: загрузка тарифной матрицы клиента (XLSX по шаблону) — зоны, весовые ступени, надбавки, правила скидок. Локальный тарификатор считает цену сам.

**FR-9.3.** Локальный тарификатор обязан поддерживать неоднородные скидочные правила, в частности типовое для рынка: **скидка применяется только к экспресс-доставке в весовых ступенях до 0,25 / 0,5 / 1 кг и не применяется к каждому последующему килограмму; на сборные грузы скидка не действует вовсе.** Правило описывается декларативно в конфигурации тарифа, а не кодом.

**FR-9.4.** Расхождение локально рассчитанной цены с фактически выставленной ТК фиксируется как отклонение и попадает в отчёт — это точка контроля корректности тарифных матриц.

### FR-10. Публичное API и интеграция

**FR-10.1.** REST, JSON, версионирование в пути (`/v1/`). OpenAPI 3.1-спецификация генерируется автоматически и публикуется.

**FR-10.2.** Аутентификация по API-ключу в заголовке `X-Api-Key`; ключи выпускаются в кабинете, имеют scope и срок действия, отзываются мгновенно.

**FR-10.3.** Лимиты: 60 запросов/мин на ключ для расчёта, 120 запросов/мин для остальных методов, 429 с заголовком `Retry-After`.

**FR-10.4.** Sandbox-контур с тестовыми учётными записями ТК и предсказуемыми ответами.

**FR-10.5.** Все ошибки — в едином формате: `{"error": {"code", "message", "field", "carrier_code", "request_id"}}`. `request_id` присутствует в каждом ответе и в логах.

### FR-11. Уведомления

**FR-11.1.** Каналы MVP: e-mail и Telegram-бот. SMS — очередь 2.

**FR-11.2.** События: отправление доставлено, отправление просрочено, риск срыва срока, ошибка создания у ТК, отсутствие событий трекинга более 5 суток, отказ авторизации у ТК.

**FR-11.3.** Настройка подписок на уровне пользователя. Дайджест или мгновенно — на выбор.

**FR-11.4.** Все уведомления на русском языке, включая тему письма и текст push/Telegram-сообщения.

### FR-12. Администрирование платформы

**FR-12.1.** Управление тенантами: создание, приостановка, лимиты, план.

**FR-12.2.** Мониторинг адаптеров: доля успешных вызовов, среднее время ответа, ошибки по кодам, за 24 часа и 30 дней. Автоматическое отключение адаптера при доле ошибок > 50 % за 15 минут с уведомлением дежурного.

**FR-12.3.** Очередь ручного сопоставления городов и услуг.

**FR-12.4.** Управление весами скора и версиями формулы.

## 8. Интеграции с перевозчиками

### 8.1. Состав очереди 1

| Перевозчик | Статус в MVP | Что известно / что уточнить |
|---|---|---|
| **СДЭК** | Обязательно, **первый адаптер** | API 2.0. Калькулятор тарифов работает без авторизации, но без персональных скидок; для создания заказов нужен договор, `client_id` и `client_secret` выдаются в личном кабинете в разделе API-доступа. Доступы к сервису интеграции запрашиваются отдельно и не совпадают с доступами от ЛК. Есть тестовый контур `integration.edu.cdek.ru`, подписка на вебхуки по статусам заказов и печатных форм, асинхронный запрос печатной формы накладной |
| **Major Express** | Обязательно, второй адаптер | Доступ к API есть, выданы оба контура — клиентский и агентский. Портал разработчика `developers.major-express.ru`. Веб-сервисы разделены по продуктам «Экспресс-доставка» и «Сборные грузы»; внутри — методы по заказам, накладным, консолидации, манифестам, клиентам, агентам, расчётам и справочникам, плюс методы без авторизации. В MVP берём только «Экспресс-доставку» |
| **Деловые Линии** | Обязательно | `dev.dellin.ru`. API бесплатное, покрывает расчёт стоимости, справочник терминалов, создание заявок на перевозку и получение информации по заказам; поддерживаются схемы терминал—терминал, дверь—дверь и предзаказ. Форматы XML и JSON, публичные и авторизованные методы, справочники по кодам КЛАДР |
| **ПЭК** | Третий адаптер, **очередь MVP-2** | `pecom.ru/business/developers`. Публичный API калькулятора работает **без регистрации и без ключа** — отладку расчёта можно начать до получения доступов. API личного кабинета покрывает заявки, статусы и печатные формы, есть тестовый контур `test-kabinet.pecom.ru`. Расчёт принимает ИНН контрагента и возвращает цену с учётом его спецусловий — то есть персональные цены доступны через API без загрузки тарифных матриц. **Внимание: сборные грузы требуют расширения доменной модели** (объём в м³, паллеты и обрешётка, филиал оплаты, типы заказа: самопривоз, забор от отправителя, отдельный заказ на машину) |
| Деловые Линии | Четвёртый адаптер, очередь MVP-2 | См. выше |
| Почта России, Boxberry | Очередь 2 | Состав и приоритет определяются заказчиком после пилота |

**Важное ограничение по всем трём:** боевой доступ к API выдаётся только при наличии действующего договора с перевозчиком. Это внешняя зависимость, которая не устраняется разработкой. Договоры и доступы должны быть получены **до начала спринта интеграций**, иначе срок сдвигается.

### 8.2. Обязательное для каждого адаптера

1. Отдельный набор интеграционных тестов на sandbox-контуре ТК.
2. Записанные фикстуры реальных ответов (VCR-подход) для офлайн-прогонов CI.
3. Карта соответствия статусов ТК → нормализованные статусы, вынесенная в YAML, а не в код.
4. Карта кодов ошибок ТК → внутренние коды с русскоязычными формулировками.
5. Обработка троттлинга ТК: соблюдение лимитов, экспоненциальные ретраи, circuit breaker.
6. Логирование сырых запросов и ответов с маскированием персональных данных и секретов, срок хранения 30 суток.

### 8.3. Порядок разработки адаптеров

Порядок: **СДЭК → Major Express → ПЭК → Деловые Линии**.

Первым делается **СДЭК**: по ней идёт реальный поток первого тенанта, договор действует, доступы берутся в его личном кабинете. Документация у неё же самая полная, что удобно для отладки самого контракта `CarrierAdapter`.

Вторым — **Major Express**. Своего потока у неё в первом тенанте нет, но без второго экспресс-перевозчика не проверяется сравнение (FR-5), а это ядро продукта: СДЭК и ПЭК относятся к разным классам перевозки и почти не пересекаются в одной выдаче. Доступ к Major Express уже есть, ожидание нулевое.

Третьим — **ПЭК**, уже в MVP-2, вместе с расширением доменной модели под сборные грузы. В MVP-1 модель остаётся экспресс-ориентированной, чтобы не тащить сборные в фундамент до появления адаптера, который их использует.

Четвёртыми — **Деловые Линии**. Каждый следующий адаптер начинается только после приёмки предыдущего, иначе интерфейс придётся переписывать четырежды.

## 9. Нормализация статусов

Единая модель состояний. Каждый адаптер обязан отобразить свои статусы в этот набор.

| Код | Значение | Финальный |
|---|---|---|
| `CREATED` | Заказ создан в системе ТК | нет |
| `ACCEPTED` | Заявка подтверждена перевозчиком | нет |
| `PICKED_UP` | Груз принят у отправителя | нет |
| `AT_ORIGIN_HUB` | На складе города отправления | нет |
| `IN_TRANSIT` | В пути между городами | нет |
| `AT_DESTINATION_HUB` | Прибыл в город назначения | нет |
| `OUT_FOR_DELIVERY` | Передан на доставку получателю | нет |
| `READY_FOR_PICKUP` | Готов к выдаче в ПВЗ/на терминале | нет |
| `DELIVERY_ATTEMPT_FAILED` | Неудачная попытка доставки | нет |
| `DELIVERED` | Доставлено | да |
| `RETURN_IN_PROGRESS` | Оформлен возврат, груз едет обратно | нет |
| `RETURNED` | Возвращён отправителю | да |
| `CANCELLED` | Отменено | да |
| `EXCEPTION` | Проблема: утеря, повреждение, таможня, отказ | нет |

**Правила:**
- Переход в финальный статус останавливает polling.
- Статус ТК, который не удалось сопоставить, пишется как есть, отправление получает `IN_TRANSIT` и попадает в очередь на ручное сопоставление в админке.
- Порядок событий восстанавливается по `occurred_at`, а не по времени получения — перевозчики регулярно отдают события с задержкой и не по порядку.
- Регресс статуса (событие «в пути» после «доставлено») не переписывает финальный статус, но фиксируется в ленте.

## 10. Методика Carrier Score

### 10.1. Формула

Скор в диапазоне 0–100:

```
Score = 100 × (0.35·OnTime + 0.20·Reliability + 0.20·IncidentFree
               + 0.15·PriceIndex + 0.10·DataQuality)
```

| Компонент | Расчёт | Смысл |
|---|---|---|
| `OnTime` | доля отправлений, доставленных не позже планового срока | ключевой показатель |
| `Reliability` | 1 − доля отправлений, отменённых или сорванных по вине ТК, и отправлений с «зависшим» трекингом | предсказуемость |
| `IncidentFree` | 1 − доля отправлений с зафиксированным инцидентом (повреждение, утеря, недостача) | сохранность |
| `PriceIndex` | нормированное положение цены относительно медианы по выборке в том же разрезе, обрезано в [0; 1] | цена как часть качества, но с малым весом |
| `DataQuality` | доля отправлений с ≥ 3 событиями трекинга и корректным финальным статусом | прозрачность перевозчика |

Веса — конфигурация, версия формулы сохраняется в снапшоте.

### 10.2. Проблема холодного старта

Это главный риск функции. На старте данных нет, а показывать выдуманную цифру нельзя — один неверный совет в первый месяц дороже, чем отсутствие функции.

Решения, обязательные к реализации:

1. **Байесовское сглаживание.** Каждый компонент считается как
   `(наблюдаемое × n + среднее_по_платформе × m) / (n + m)`, где `m = 20` (приорный вес). При малой выборке скор притягивается к среднему и не даёт выбросов.
2. **Каскад разрезов.** Нет данных по `direction_weight` → берём `direction` → берём `global`. Разрез, из которого взято значение, показывается пользователю.
3. **Явный статус доверия** (FR-7.3). При `insufficient` в интерфейсе выводится «недостаточно данных», а не число.
4. **Заявленный SLA как временный ориентир.** Пока нет фактики, в колонке риска показывается только заявленный перевозчиком срок с пометкой, что фактическая статистика ещё не накоплена.

### 10.3. Что закладывается на будущее

Модель данных должна позволить перейти к обучаемой модели без переделки: сохраняются все признаки (город отправления и назначения, вес, объём, тип груза, день недели, месяц, тариф, цена, наличие забора, объявленная ценность) и целевая переменная (фактическое отклонение в днях, факт инцидента). Обучение модели — вне MVP.

## 12. Безопасность и персональные данные

**12.1.** Размещение всей инфраструктуры и данных на территории РФ (152-ФЗ, ст. 18 ч. 5). Персональные данные получателей (ФИО, телефон, адрес) — обрабатываются как ПДн.

**12.2.** Уведомление в Роскомнадзор об обработке ПДн, политика обработки ПДн, согласия и поручения на обработку в договоре с тенантом. Юридический пакет готовится параллельно разработке.

**12.3.** Шифрование: TLS 1.2+ снаружи, шифрование учётных данных перевозчиков в БД (AES-GCM), пароли — Argon2id.

**12.4.** RBAC на уровне сервиса + Row Level Security на уровне БД.

**12.5.** Обязательная двухфакторная аутентификация для роли `owner`, опциональная для остальных.

**12.6.** Аудит-лог всех изменяющих операций и всех обращений службы поддержки к данным тенанта.

**12.7.** Маскирование ПДн в логах и в трассировках. Полные значения — только в БД.

**12.8.** Ограничение частоты и защита от перебора на публичной странице трекинга.

**12.9.** Перед промышленным запуском — внешнее тестирование на проникновение и сканирование зависимостей в CI.

## 14. Тестирование и критерии приёмки

### 14.1. Уровни тестирования

- Модульные тесты: покрытие бизнес-логики (тарификатор, нормализация статусов, расчёт скора, рабочий календарь) ≥ 80 %.
- Интеграционные тесты адаптеров: на sandbox ТК + на записанных фикстурах.
- E2E: сквозные сценарии С-1, С-2, С-3 в автоматическом прогоне.
- Нагрузочное тестирование: 20 расчётов/с в течение 10 минут без деградации p95 выше цели.
- Тест изоляции тенантов: попытка доступа к чужим данным по прямому идентификатору должна возвращать 404, а не 403.

### 14.2. Критерии приёмки MVP

MVP считается принятым, если выполнено всё перечисленное:

1. Три адаптера (СДЭК, Major Express, Деловые Линии) проходят полный цикл: расчёт → создание → этикетка → трекинг до финального статуса → отмена (где поддерживается) на боевых учётных записях.
2. Расчёт по трём ТК возвращает выдачу за ≤ 5 секунд в 95 % случаев на выборке из 200 запросов.
3. Отказ или таймаут одного ТК не мешает получить выдачу от остальных.
4. Создание отправления идемпотентно: 100 повторных запросов с одним `Idempotency-Key` дают один заказ у ТК.
5. Сверка «призраков» отрабатывает: имитация обрыва связи после создания заказа приводит к корректной досинхронизации в течение 15 минут.
6. Лента трекинга по 100 контрольным отправлениям совпадает с личными кабинетами ТК по составу финальных статусов.
7. Пакетная загрузка 1 000 строк обрабатывается за ≤ 10 минут, ошибки возвращаются построчно.
8. Печать: пакетный PDF на 100 этикеток формируется за ≤ 30 секунд.
9. Отчёт «План vs факт» сходится с ручной выборкой из БД на контрольном наборе.
10. Carrier Score корректно показывает `insufficient` при выборке < 10 и не подставляет глобальное значение молча.
11. Тест изоляции тенантов пройден.
12. Опубликована OpenAPI-спецификация, sandbox доступен, есть руководство по интеграции на русском языке.
13. Развёртывание с нуля по документации занимает ≤ 2 часов на чистом окружении.

## 17. Очередь 2 (не входит в MVP, влияет на архитектуру)

Перечислено, чтобы решения MVP не закрыли эти направления:

1. **Обмен с 1С** — OData/REST, выгрузка отправлений и стоимостей, сопоставление контрагентов.
2. **Cargo Control** — интеграция индикаторов удара, наклона, температуры и вскрытия (ШокЛог, BLE/RFID-метки). События пишутся в `shipment_events` с `source = sensor`; связка с Carrier Score и претензионной работой — главный дифференциатор второй очереди.
3. **Претензионный модуль** — от инцидента к претензии с доказательной базой (данные датчика + лента трекинга + фото).
4. **Биллинг и логистическая маржа** — SaaS-подписка, транзакционная плата, маржа на ставках Aerogram.
5. **Возвраты.**
6. **Расширение перевозчиков** — Почта России, Boxberry, ПЭК, региональные ТК, международные операторы.
7. **AI Routing** — обучаемая модель выбора перевозчика на накопленных данных.
8. **Сборные грузы, авиа, международная экспресс-доставка**, далее море и ж/д.

## 18. Открытые вопросы к заказчику

1. Юридическая схема на пилоте: платформа выступает агентом перевозчика, посредником или только ИТ-сервисом без участия в расчётах? От этого зависит, нужен ли в MVP хотя бы минимальный учёт взаиморасчётов.
2. Кто первые 5 пилотных клиентов и есть ли у них действующие договоры с тремя выбранными ТК? Без этого не собрать данные для скора.
3. Нужен ли режим white-label (кабинет под брендом клиента) — влияет на фронтенд-архитектуру, дешевле заложить сразу.
4. Требуется ли on-premise-вариант поставки для крупных клиентов — влияет на упаковку и лицензирование.
5. Целевая политика по хранению ПДн получателей: срок хранения и порядок обезличивания после доставки.
6. Приоритет очереди 2: Cargo Control или обмен с 1С? Первый сильнее как дифференциатор, второй быстрее продаётся.
