# ADR-0021. Массовая рассылка писем Почтой России — второй продукт, а не адаптер

**Статус:** ПРЕДЛОЖЕНО — решение за человеком
**Дата:** 4 сентября 2026

## Контекст

Поставлена задача: сделать массовую рассылку обычных и заказных писем через
Почту России, «как у catapulto.ru».

Разбор показал, что это **не адаптер перевозчика и не стадия ADR-0020**.
Контракт `CarrierAdapter` описывает жизненный цикл одного отправления:
`quote → create → label → track → cancel`. Массовая рассылка устроена иначе:

```
список адресов → нормализация → отправления пачкой → партия →
Ф.103 → передача в ОПС → трекинг пачкой
```

Здесь нет расчёта по вариантам и нет выбора перевозчика — то есть нет
Decision Engine, ради которого написано всё ядро. Втиснуть это в
`CarrierAdapter` значит либо изуродовать контракт, который меняется только
через ADR (CLAUDE.md §7, пункт 3), либо получить адаптер, у которого шесть
методов из восьми поднимают исключение.

Поэтому вопрос к человеку — не «как писать», а **«делаем ли мы второй
продукт»**.

## Что установлено по API Почты

Хорошая новость: **весь нужный контракт у Почты есть**, он официальный
и уже лежит в репозитории (`docs/integrations/sources/pochta/otpravka/`,
117 страниц, ADR-0020). Ничего изобретать не придётся.

| Что нужно рассылке | Метод Почты |
|---|---|
| Разбор строки адреса, поиск индекса | `POST /1.0/clean/address` |
| Разбор ФИО и телефона | `POST /1.0/clean/physical`, `/1.0/clean/phone` |
| Создание отправлений пачкой | `PUT /1.0/user/backlog` |
| Сборка партии из N заказов | `POST /1.0/user/shipment` |
| Ведение партии | `batches/*` — добавить, перенести, удалить, найти |
| **Ф.103 — список для сдачи в ОПС** | `GET /1.0/forms/{id}/f103pdf` |
| Ярлыки и конверты | `documents/*`, тип конверта C4/C5/C6/DL/A6 |
| Электронная сдача в ОПС | `sessions/*`, `documents/checkin` |
| Трекинг | WSDL `tracking.russianpost.ru/fc` — **пакетный**, по билету |

Виды и категории отправлений, которые нужны именно письмам, в справочниках
есть: `mail-type` = `LETTER` («Письмо»), `LETTER_CLASS_1` («Письмо 1-го
класса»), `BANDEROL`; `mail-category` = `SIMPLE` («Простое»), `ORDERED`
(«Заказное»), `WITH_DECLARED_VALUE`.

Три факта, которые определяют архитектуру, а не оформление:

**1. Пригодность адреса определяет Почта, а не мы.** Документация метода
нормализации задаёт правило дословно: «Адрес считается корректным к отправке,
если `quality-code` = `GOOD`, `POSTAL_BOX`, `ON_DEMAND` или `UNDEF_05`;
`validation-code` = `VALIDATED`, `OVERRIDDEN` или `CONFIRMED_MANUALLY`».
Значит у рассылки есть отдельное состояние «адрес не принят» и отдельный
экран разбора — на списке в 50 000 строк это не исключение, а норма.

**2. Суточная квота вызовов — предмет проектирования, а не мелочь.**
Почта отдаёт её методом `GET /1.0/settings/limit`: «количество запросов
по API, разрешённых для клиента» и остаток на сутки. Рассылка в 50 000 писем
— это десятки тысяч вызовов на нормализацию и создание. Если квота меньше
размера рассылки, продукт обязан уметь **растягивать её на несколько суток**
и переживать перезапуск. Это влияет на схему БД и на очередь задач.

**3. Трекинг писем пакетный.** Единичный `getOperationHistory` на 50 000
отправлений неприменим. Пакетный контур `FederalClient` работает по билетной
схеме `getTicket → getResponseByTicket` — асинхронно, с ожиданием. Это другой
опрос, чем у посылочных перевозчиков.

## Чего я не видел

**Catapulto.ru недоступен** из окружения разработки: шлюз отвечает `403`
на `CONNECT` — домена нет в сетевой политике. Ни одной страницы их сервиса
я не открывал, и всё написанное выше выведено из документации Почты,
а не из чужого продукта.

Если нужен разбор именно их решения — добавьте `catapulto.ru` в разрешённые
домены окружения, и я посмотрю: что у них в тарифах, какой шаг воронки,
что они делают с непринятыми адресами. Копировать чужой интерфейс не нужно
и незачем, а вот увидеть, какие возможности клиенты считают обязательными,
полезно.

## Что предлагается решить

**1. Делаем ли второй продукт.** Массовая рассылка — не расширение
Decision Engine, а соседний продукт на общей инфраструктуре (тенанты, RLS,
деньги, документы, очередь задач). Это отдельный модуль `mailing/`, свои
таблицы, свои экраны и свой раздел ТЗ. Оценка — сопоставима с двумя
адаптерами: там, где у адаптера один заказ, здесь список, партия, разбор
ошибок и печать.

**2. Если делаем — что входит в первую версию.** Предлагаемый минимум,
который уже полезен:

* загрузка списка (CSV/XLSX) и нормализация адресов пачкой;
* очередь разбора непринятых адресов — с ручной правкой;
* создание отправлений и сборка партии;
* Ф.103 и конверты на печать;
* передача партии в ОПС и пакетный трекинг.

Вне первой версии: печать самих писем, слияние с шаблоном, оплата марок,
возвраты, электронные заказные письма (ЭЗП) — каждое тянет своё.

**3. Порядок относительно ADR-0020.** Очередь адаптеров сейчас:
Деловые Линии ✅ → ПЭК ✅ → **Почта России** → Яндекс. Адаптер Почты (посылки,
трекинг по WSDL) и рассылка писем — разные работы по одному перевозчику.
Что раньше? Рассылка ближе к деньгам клиента, адаптер ближе к обещанному
пилоту на шесть перевозчиков.

**4. Персональные данные.** Это главный риск, и он не технический.
Рассылка означает обработку списков физических лиц — ФИО и адресов, десятками
тысяч. У платформы уже числится незакрытым «Юридический пакет по персональным
данным» (`docs/status.md`, «Перед выпуском MVP», пункт 3): уведомление
в Роскомнадзор, политика обработки, поручение на обработку в договоре
с тенантом. Для рассылки этот пакет **обязателен до первого загруженного
списка**, а не до запуска: загруженный список — это уже обработка.
Отдельно потребуется решение о сроке хранения списков и о том, кто
и по какому основанию их видит.

## Последствия

Пока решение не принято, код не пишется — как и в ADR-0020. Разведка при
этом не пропадает: документация Почты уже в репозитории, и когда решение
будет принято, работа начинается с проектирования схемы (CLAUDE.md §7,
пункт 1), а не с чтения чужих сайтов.
