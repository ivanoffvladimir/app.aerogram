# ADR-0003. Изоляция тенантов через Row Level Security

**Статус:** принято
**Дата:** 29 августа 2026

## Контекст

Модель мультитенантности задана ТЗ (раздел 4.4): общая база, общая схема,
обязательная колонка `tenant_id`. Вопрос в том, чем обеспечивается изоляция.

## Решение

Row Level Security на уровне PostgreSQL, дополнительно к коду приложения:

* на каждой бизнес-таблице `ENABLE` и `FORCE ROW LEVEL SECURITY`;
* политика `tenant_isolation` сравнивает `tenant_id` с настройкой сессии
  `app.tenant_id`;
* приложение подключается ролью **без** атрибута `BYPASSRLS`;
* миграции выполняются отдельной ролью;
* каждая транзакция начинается с `set_config('app.tenant_id', …, true)`.

Миграция: `alembic/versions/20260829_0002_tenant_isolation.py`.

## Обоснование

Изоляция только на уровне приложения держится на том, что в каждом из сотен
запросов кто-то не забыл `WHERE tenant_id = …`. Это гарантия, которую нельзя
проверить — ни ревью, ни тестами на весь объём кода. Утечка данных между
клиентами убивает B2B-продукт целиком, поэтому цена ошибки несимметрична.

RLS переносит гарантию туда, где её нельзя обойти по невнимательности.

Важная деталь реализации: предикат записан как
`nullif(current_setting('app.tenant_id', true), '')::uuid`. Прямое приведение
`''::uuid` роняет любой запрос ошибкой типа вместо того, чтобы просто не отдать
строк. Это обнаружилось тестом `test_no_tenant_set_returns_nothing`.

## Последствия

* Незаданный тенант означает пустую выдачу, а не ошибку. Это желаемое поведение
  до аутентификации.
* Появление новой бизнес-таблицы требует политики в миграции. Тест
  `test_every_tenant_table_has_rls_forced` выводит список таблиц из моделей
  и падает, если политику забыли.
* Роль приложения не может создавать тенантов — этим занимается платформенный путь.
