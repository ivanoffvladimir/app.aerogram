# ADR-0004. Окно поиска пользователя при входе

**Статус:** принято
**Дата:** 29 августа 2026

## Контекст

RLS изолирует таблицу `users` по `app.tenant_id` (ADR-0003). Но в момент входа
тенант ещё неизвестен: пользователь предъявляет только e-mail и пароль. Обычная
политика не находит его ни в одном тенанте.

Рассмотренные варианты:

1. **Логин с указанием компании.** Пользователь выбирает тенанта до ввода пароля.
   Отвергнуто: лишний шаг в основном сценарии и необходимость публично раскрывать
   список компаний либо заводить отдельные поддомены.
2. **Функция `SECURITY DEFINER` под ролью с `BYPASSRLS`.** Технически чище всего,
   но требует роли с `BYPASSRLS` и прав суперпользователя при развёртывании. Это
   усложняет требование «развёртывание с нуля за 2 часа» (раздел 9.4 ТЗ) и создаёт
   роль, компрометация которой снимает изоляцию полностью.
3. **Отдельная платформенная таблица «e-mail → тенант».** Дублирование данных
   и второй источник правды о пользователях.

## Решение

Отдельная политика на таблице `users`, действующая только на `SELECT`:

```sql
CREATE POLICY users_auth_lookup ON users
    FOR SELECT
    USING (current_setting('app.auth_scope', true) = 'login');
```

Настройка `app.auth_scope` устанавливается транзакционно
(`set_config(..., is_local => true)`) в **единственном** месте кода —
`aerogram.core.service.AuthService._lookup_user` — и сбрасывается сразу после
поиска.

## Обоснование

Это осознанный компромисс, а не недосмотр. Его границы:

* окно открывается только на чтение — запись остаётся под общей политикой;
* окно охватывает только таблицу `users`; остальные таблицы недоступны, что
  проверяется тестом `test_login_window_is_scoped_to_users_only`;
* окно транзакционное и не переживает возврат соединения в пул;
* второе место, открывающее окно, ловится тестом
  `tests/unit/test_auth_scope_guard.py` — он читает исходники и падает, если
  константа упоминается где-то ещё.

## Последствия

* Ошибка в `AuthService._lookup_user` (например, забытый сброс) означала бы
  видимость всех пользователей в рамках одной транзакции. Поэтому сброс
  выполняется в `finally`, а метод покрыт тестами.
* При переходе на вход по поддоменам тенанта эту политику следует удалить.
