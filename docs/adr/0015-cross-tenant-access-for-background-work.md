# ADR-0015. Доступ к данным вне контекста запроса

**Статус:** ПРЕДЛОЖЕНО — решение за человеком, реализации по нему ещё нет
**Дата:** 30 августа 2026

## Контекст

Роль приложения работает под `FORCE ROW LEVEL SECURITY` и без установленного
`app.tenant_id` не видит ничего. Это верно и желательно для HTTP-запроса,
где тенант известен из токена. Но четыре сценария происходят **вне запроса**.

Важное уточнение, снимающее часть вопроса: таблица `tenants` платформенная,
RLS на неё не распространяется, и роль приложения может перечислить тенантов.
Поэтому фоновые задачи **уже работают** — они обходят тенантов по одному
и открывают на каждого обычную транзакцию с установленным тенантом
(`worker/tasks.py`). Никаких новых прав это не требует.

Нерешёнными остаются те сценарии, где обход по одному не годится.

## Что требует решения

### 1. Приём вебхуков от перевозчика (FR-3.1)

Вебхук приходит **без контекста тенанта**: перевозчик знает только свой
идентификатор заказа. Найти отправление можно лишь поиском по всем тенантам.

Варианты:

| Вариант | Чего стоит |
|---|---|
| Узкое окно `app.auth_scope = 'webhook'`: SELECT по `shipments` только по `carrier_id + external_id` | Четвёртое окно по образцу ADR-0004; миграция; окно живёт постоянно |
| Перебор тенантов до совпадения | Ноль изменений схемы, но O(тенантов) запросов на каждый вебхук; на пилоте приемлемо, на сотне клиентов нет |
| Отдельная таблица-указатель `external_id → shipment_id` без RLS | Ещё одна таблица и её синхронизация; зато поиск точечный |

Отдельно нужен ответ: **где хранится секрет подписи** и что делать, когда
одного перевозчика используют несколько тенантов — по какому ключу выбирать
секрет для проверки подписи, если тенант ещё не определён.

### 2. Свод Carrier Score по платформе (раздел 10.2)

Приор «среднее по платформе» требует данных всех тенантов. Обход тенантов
с суммированием счётчиков в приложении это даёт, но:

**Это вопрос не только доступа, но и приватности.** Скор перевозчика,
посчитанный по данным трёх клиентов, показывается четвёртому. Если
перевозчиком пользуется один тенант, его скор — это статистика этого
тенанта, показанная остальным. Нужен ответ: считаем ли скор общим благом
платформы, и если да — какой минимальный размер выборки и число тенантов
делают его обезличенным.

Сейчас `recalculate` считает по тому, что видит сессия, то есть по одному
тенанту, и снапшот последнего пересчёта затирает предыдущий. Это временная
замена своду, а не он.

### 3. Ключ разреза `direction` (FR-7.2)

Модель описывает его как пару кодов регионов (`RU-PRI>RU-MOW`), но регион
в адресе контракта необязателен и в наших снимках обычно пуст. Варианты:
брать регион из ФИАС по разрешённому городу; строить ключ по парам городов
(дробит и без того малую выборку); отказаться от разреза до появления данных.

### 4. Отдельная роль БД для фоновых задач — нужна ли

Обход тенантов стоит одной транзакции на тенанта за цикл. На пилоте это
единицы транзакций в минуту. Когда тенантов станут сотни, встанет выбор:
оставить обход или завести роль с `BYPASSRLS` для воркера и аналитики.

Второе быстрее, но снимает единственную защиту, которую нельзя обойти
забытым `WHERE`. Если такая роль появится, нужно решить: какие таблицы,
только чтение или запись, откуда берутся её учётные данные и как в аудите
отличать её действия от действий пользователя.

## Побочная находка

`tenants` не под RLS, и роль приложения может прочитать список всех компаний
с их ИНН. Ни один эндпоинт этого не отдаёт, но возможность есть.
Формально правило CLAUDE.md («каждая бизнес-таблица имеет `tenant_id`
и политику RLS») к ней не применимо: у неё нет колонки `tenant_id`, её
идентификатор и есть тенант. Нужно ли закрывать — вопрос того же ревью.

## Последствия

До решения по пункту 1 путь `POST /v1/webhooks/{carrier_code}` остаётся
в списке нереализованных, а трекинг живёт на опросе. До решения по пункту 2
скор считается по одному тенанту и в выдачу расчёта не подставляется
(FR-7.6 не закрыт).
