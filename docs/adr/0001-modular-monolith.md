# ADR-0001. Модульный монолит вместо шести сервисов

**Статус:** принято
**Дата:** 29 августа 2026

## Контекст

Функциональная часть ТЗ (раздел 4.1) описывает шесть отдельных сервисов: `api-gateway`,
`core-service`, `rating-service`, `tracking-service`, `document-service`, `score-service`.

Фактические условия проекта другие: один разработчик с ИИ-агентами, один VPS,
эксплуатация в одиночку.

## Решение

Один процесс приложения + один процесс воркера + одна база данных. Модули из
функционального ТЗ сохраняются как **границы пакетов внутри монолита**, а не как
сетевые сервисы.

Границы обеспечивает `import-linter` (файл `.importlinter`), а не HTTP.

## Обоснование

Шесть сервисов для одного человека — это шесть деплоев, шесть наборов миграций,
распределённая отладка и межсервисные контракты. Всё это съест больше времени,
чем сэкономит.

Отдельно важно для работы с ИИ-агентами: агент читает 3–5 файлов одного модуля
вместо обхода межсервисных контрактов. Это прямо влияет на качество генерации
и на расход контекста.

## Последствия

* Горизонтальное масштабирование `rating` отдельно от остального невозможно
  без выделения сервиса. В нагрузке MVP (20 расчётов/с) это не требуется.
* Выделение `rating` и `tracking` в самостоятельные сервисы остаётся возможным
  позже: модульная структура позволит это без переписывания домена.
* Нарушение границы модуля становится ошибкой CI, а не предметом договорённости.
