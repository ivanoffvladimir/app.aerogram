# ADR-0022. Схема массовых отправлений: две таблицы поверх Decision Engine

**Статус:** ПРЕДЛОЖЕНО — схема БД требует построчного просмотра (CLAUDE.md §7, пункт 1)
**Дата:** 4 сентября 2026

## Контекст

Решением по ADR-0021 выбран вариант «Б» — массовые отправления, то, что делает
catapulto: один отправитель, много получателей, расчёт и оформление списком,
приоритет «цена или скорость» на каждого получателя и персональная замена
тарифа по строке.

Разбор их продукта показал, что вся предметная машина у нас уже есть
(`docs/integrations/catapulto-mass-shipments.md`). Значит вопрос сводится
к одному: **какие сущности добавить, чтобы не продублировать существующие.**

## Решение

Две таблицы. Ни одна из них не хранит того, что уже хранят
`rate_quotes`, `recommendations`, `decisions` и `shipments`, — только
ссылается.

### `bulk_runs` — массовый расчёт

Черновик и его жизненный цикл. Одна строка — один «массовый расчёт»
в терминах кабинета.

| Колонка | Тип | Зачем |
|---|---|---|
| `id` | UUIDv7 | |
| `tenant_id` | UUID | RLS, как у всех бизнес-таблиц |
| `user_id` | UUID NULL | кто создал |
| `name` | VARCHAR(120) | по умолчанию — дата, правится вручную |
| `status` | VARCHAR(20) | `draft → quoting → quoted → creating → completed`, плюс `failed` |
| `strategy` | VARCHAR(20) NULL | приоритет: та же стратегия, что у одиночного расчёта |
| `sender_snapshot` | JSONB | отправитель на момент создания — неизменяем |
| `created_at`, `updated_at` | TIMESTAMPTZ | |

### `bulk_rows` — строка списка

Один получатель. Здесь же ссылки на всё, что уже умеет платформа.

| Колонка | Тип | Зачем |
|---|---|---|
| `id` | UUIDv7 | |
| `tenant_id` | UUID | RLS |
| `run_id` | UUID → `bulk_runs` ON DELETE CASCADE | |
| `position` | INTEGER | порядок в списке, уникален внутри прогона |
| `recipient_snapshot` | JSONB | получатель на момент добавления |
| `cargo_snapshot` | JSONB | груз этой строки |
| `rate_quote_id` | UUID → `rate_quotes` NULL | расчёт строки |
| `recommendation_id` | UUID → `recommendations` NULL | рекомендация строки |
| `decision_id` | UUID → `decisions` NULL | выбор строки |
| `shipment_id` | UUID → `shipments` NULL | созданное отправление |
| `status` | VARCHAR(20) | `new → quoted → selected → created`, плюс `failed` |
| `error_message` | TEXT NULL | почему строка не прошла |

Ограничения: `UNIQUE (run_id, position)`; `CHECK`, что строка со статусом
`failed` объясняет причину; `CHECK`, что `created` невозможен без
`shipment_id`. RLS `FORCE ROW LEVEL SECURITY` на обеих таблицах.

## Почему именно так

**Персональная замена тарифа не требует ничего нового.** «Карандаш» напротив
получателя — это `Decision` с `override = true` и причиной из закрытого
списка. Он уже реализован, уже попадает в метрику Override Rate и уже
показывается на дашборде. Отдельного поля в `bulk_rows` для этого нет
намеренно: дублировать смысл в двух местах значит однажды их рассинхронизировать.

**Снимки — JSONB, ссылки — колонки.** `sender_snapshot`, `recipient_snapshot`
и `cargo_snapshot` неизменяемы и не фильтруются, поэтому JSONB (CLAUDE.md §6).
Всё, по чему ищут и считают — статус, позиция, ссылки, — живёт в колонках.

**Идемпотентность выводится, а не запрашивается.** `decisions` требует
`idempotency_key`, уникальный в пределах тенанта. Для строки прогона ключ
детерминированный: `bulk:{run_id}:{row_id}`. Повтор всего прогона тогда
безопасен — повторные строки вернут те же решения, а не создадут вторые.
Это и есть ответ на «что будет, если оператор нажмёт „создать“ дважды».

**Частичный успех — нормальное состояние.** Прогон из 500 строк, где 3 не
прошли, — не ошибка прогона. Поэтому статус есть и у прогона, и у строки,
а причина отказа хранится построчно. Прогон считается `completed`, когда
ни одна строка не осталась в работе, даже если часть строк `failed`.

**Ничего не пересчитывается задним числом.** `rate_quotes` и `decisions`
неизменяемы после принятия решения (CLAUDE.md §6), и прогон на них только
ссылается. Повторный расчёт строки создаёт новый `rate_quote`, а не правит
старый.

### Экран кабинета

Реестр прогона живёт по `/bulk/view?id=…`, а не сегментом пути. Кабинет
собирается статическим экспортом (ADR-0012), а тот требует знать значения
динамического сегмента на сборке — идентификаторы же появляются в рантайме
и у каждого тенанта свои. Так же сделана карточка отправления.

**Кнопка следующего шага выводится из счётчиков строк, а не из статуса
прогона.** Статуса для этого не хватает: после расчёта и после выбора тарифа
прогон одинаково `quoted` — он в работе и там и там, — и кнопка по статусу
предлагала бы посчитать заново уже посчитанное. Счётчики же повторяют ровно
те условия, по которым сервер пропускает строку: `quote` берёт `new`,
`select` — `quoted`, `create` — `selected`. Когда брать нечего, кнопки нет:
кнопка, которая ничего не изменит, заставляет оператора гадать, почему
ничего не произошло.

Ввод получателей — текстом, «город; адрес» по строке, и в интерфейсе он
назван временным. Импорт файла и подбор по адресной книге идут второй
стадией: строить разбор чужих форматов до того, как оператор увидит
работающий прогон, значит угадывать.

### Стадия 2: импорт списка и «файл поиска»

**Разбор — на сервере, один на всех клиентов.** `POST /v1/bulk-runs/import`
принимает текст списка и возвращает разобранные строки; кабинет только
показывает. Разбирать в браузере значило бы держать два разбора — для
кабинета и для машинного клиента — и однажды получить два разных ответа
на один файл.

**Формат угадывается по заголовку, а не объявляется.** Оператор приносит
список тем, чем умеет: вставкой из письма — «город; адрес» по строке — или
выгрузкой из учётной системы, где первая строка называет столбцы. Если
в первой непустой строке есть хотя бы одно знакомое название столбца,
это таблица; разделителем считается тот из «;», «,» и табуляции, который
даёт больше всего знакомых названий. Названия принимаются русские и
английские, без регистра, пробелов и единиц в скобках: «Вес, кг» — это
вес. Переименовывать столбцы в чужой системе ради нас никто не будет.

**«Файл поиска» — подбор по собственной адресной книге тенанта**, как
у catapulto: строка с ИНН или названием контрагента находит его и берёт
его адрес. Совпадение **точное**: по ИНН — равенство, по названию —
равенство без регистра. Подстрока подобрала бы «Роспломба-Юг» вместо
«Роспломбы», а список называет получателя целиком.

**Выбор между несколькими — за оператором, не за кодом.** ИНН общий
у головной организации и филиалов, у контрагента бывает несколько адресов.
Такая строка возвращается как `ambiguous` с вариантами, и в прогон
не попадает, пока оператор не выбрал. Город, названный в строке, сужает
выбор — но только если оставил хотя бы один адрес: адрес в другом городе
это вопрос, а не «адресов нет».

**Импорт — предпросмотр, прогон не создаётся.** Оператор видит, что
распозналось, что нашлось и что нашлось неоднозначно, и только потом
создаёт расчёт обычным `POST /v1/bulk-runs` — из готовых строк. Строки,
которые не вошли, называются счётчиком, а нечитаемые — номером строки:
молча выбросить получателя из рассылки хуже, чем отказаться.

**Груз строки из файла побеждает общий.** Столбцы «вес» и «ценность»
читаются в килограммах и рублях — так пишут люди — и переводятся в граммы
(вверх, до целого) и копейки без `float`. Строка без своих значений
получает общий груз прогона.

**Импорт закрыт для машинных ключей** — как и сама адресная книга. По ИНН
можно перебрать, кто в ней есть, и открывать это тому, для кого адресная
книга закрыта, значило бы открыть её с чёрного хода.

## Что это НЕ включает

Печать самих писем, слияние с шаблоном, оплату марок — это вариант «В»
(ADR-0021), другой модуль и другая схема.

Подбор по телефону. В адресной книге телефон хранится как введён, и точное
сравнение невозможно без нормализованной колонки — а это миграция, то есть
решение человека (CLAUDE.md §7, пункт 1). Подбор по ИНН и названию
покрывает выгрузки из учётных систем; телефон нужен спискам физических лиц,
и это отдельный разговор вместе с пакетом по ПДн.

## Последствия

* Новый модуль `bulk/` со своими `models`, `repository`, `service`, `router` —
  границы модулей те же, что у остальных (CLAUDE.md §4).
* Одна миграция, обратимая. **Она требует построчного просмотра человеком**,
  и до этого просмотра не применяется нигде, кроме локальной базы и CI.
* Пакет по ПДн этот вариант не блокирует: получатели уже лежат в адресной
  книге тенанта по его собственному основанию (`docs/legal/personal-data.md`).
