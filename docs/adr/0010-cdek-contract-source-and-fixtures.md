# ADR-0010. Источник контракта СДЭК и синтетические фикстуры

**Статус:** принято, с ограничением срока действия
**Дата:** 30 августа 2026

## Контекст

Неделя 5 — расчёт по API СДЭК. Требования ТЗ к адаптеру (раздел 8.2):
интеграционные тесты на sandbox-контуре перевозчика и **записанные реальные
ответы** (VCR-подход) для офлайн-прогонов CI.

Выполнить это сейчас невозможно по двум независимым причинам:

1. Боевые доступы (`client_id` / `client_secret` из личного кабинета
   «Роспломбы») не получены. Это внешняя зависимость, разработкой она
   не устраняется, и она числится блокером в `docs/status.md` с первой недели.
2. Домены `api.cdek.ru` и `api.edu.cdek.ru` закрыты сетевой политикой
   окружения разработки: шлюз отвечает `403` на `CONNECT`. Даже с публичными
   учётными данными тестового контура запрос отсюда не уйдёт.

Оставалось два варианта: не писать адаптер до получения доступов либо писать
его по контракту, сверенному с надёжным источником, и явно пометить границу
проверенного.

## Решение

Адаптер написан. Контракт сверен с **исходниками официального SDK СДЭК
для API 2.0**, а не с памятью и не с пересказом.

Что подтверждено дословно:

| Что | Значение |
|---|---|
| Боевой контур | `https://api.cdek.ru/v2/` |
| Тестовый контур | `https://api.edu.cdek.ru/v2/` |
| Авторизация | `POST oauth/token?parameters`, `application/x-www-form-urlencoded` |
| Параметры авторизации | `grant_type=client_credentials`, `client_id`, `client_secret` |
| Ответ авторизации | `access_token`, `expires_in` (по умолчанию 3600) |
| Дальнейшие вызовы | заголовок `Authorization: Bearer <token>` |
| Расчёт по тарифам | `POST calculator/tarifflist`, ответ `{"tariff_codes": [...]}` |
| Поля тарифа | `tariff_code`, `tariff_name`, `tariff_description`, `delivery_mode`, `delivery_sum`, `period_min`, `period_max`, `calendar_min`, `calendar_max` |

Фикстуры в `tests/fixtures/cdek/` — **синтетические**. Они собраны по этому
контракту вручную и помечены как таковые в README рядом с ними.

## Обоснование

Исходник SDK — источник строже прозы документации: он исполняется, а значит
расхождение с боевым контуром обнаружилось бы у его пользователей. Ссылки
на страницы документации при этом сохранены, но сами страницы из окружения
недоступны.

Ждать доступов, ничего не делая, дороже: контракт адаптера, нормализация
тарифов, разбор ошибок и фильтрация режимов доставки от доступов не зависят,
а их проектирование — самая долгая часть работы. Когда доступы появятся,
останется прогнать записанные ответы и сверить детали.

**Чего эта работа НЕ доказывает.** Что боевой контур отвечает именно так.
Синтетическая фикстура проверяет наш разбор ответа, а не ответ.

## Что обязательно сделать при получении доступов

1. Прогнать `quote` на `api.edu.cdek.ru` и записать реальные ответы
   в `tests/cassettes/` через `pytest-recording`.
2. ~~**Сверить единицу измерения веса.**~~ **Подтверждено 31 августа 2026.**
   `packages[].weight` задаётся в граммах, внутренняя единица платформы —
   килограммы (`Place.weight_kg`), перевод делает `mapping.grams_from_kg`.

   Основание: readme официального SDK прямо помечает вес товара как
   «Вес в граммах», а пример места — `setWeight(500)` при габаритах
   10×10×10 см, что килограммами быть не может. Подтверждено человеком.

   Пункт закрыт документально, но не боевым вызовом: первый же расчёт
   на настоящих доступах стоит сверить с личным кабинетом по сумме —
   ошибка здесь не даёт исключения, она даёт цену, отличающуюся в тысячу
   раз, и обнаруживается счётом от перевозчика через месяц.
3. Сверить состав кодов `delivery_mode`: по ним фильтруется выдача
   (`mapping.modes_for_request`), и новый код у СДЭК означал бы молча
   пропавшие из выдачи тарифы. Сейчас отброшенные режимы пишутся в лог.
4. Сверить формат ошибок: реализация ожидает
   `{"errors": [{"code", "message"}]}`.

До выполнения оставшихся трёх пунктов адаптер СДЭК **не считается
проверенным**, и в `docs/status.md` он числится непроверенным на боевом
контуре.

## Последствия

* Кэш токена — в памяти процесса, не в Redis. Токен живёт час, цена лишней
  авторизации — один запрос на процесс в час; общий кэш добавил бы точку
  отказа ради экономии, которой не видно. При переходе на несколько воркеров
  решение остаётся в силе.
* Методы `create`, `cancel`, `label`, `track` и разбор вебхуков объявлены
  и **явно отказывают** с указанием недели, в которую будут сделаны. Пустой
  результат вместо отказа разошёлся бы по домену как данные: отправление
  без трек-номера, лента без событий.
