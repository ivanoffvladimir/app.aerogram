# ADR-0005. Учётные записи перевозчиков живут в `core`, а не в `carriers`

**Статус:** принято
**Дата:** 29 августа 2026

## Контекст

Функциональное ТЗ группирует `carriers`, `carrier_accounts`, `carrier_services`
и `carrier_terminals` в один раздел «Перевозчики» (5.2). При переносе в структуру
пакетов возник вопрос, где им находиться.

Ограничение раздела 6 ТЗ: `carriers` не знает о домене, принимает DTO и возвращает
DTO. Если адаптер обращается к БД, это ограничение нарушается.

## Решение

* `carriers/` — **только код адаптеров**. Ни одной модели SQLAlchemy, ни одного
  обращения к базе.
* `directories/models.py` — платформенные справочники: `carriers`,
  `carrier_services`, `carrier_terminals`, `cities`, `city_carrier_map`.
  Общие для всех тенантов, без `tenant_id` и без RLS.
* `core/models.py` — `carrier_accounts` и `carrier_raw_calls`. Обе таблицы
  принадлежат тенанту, обе — предмет требований по секретам и ПДн.

Адаптер получает уже расшифрованные учётные данные в DTO `CarrierAccount`
(`carriers/base.py`). Расшифровка — забота вызывающего слоя.

## Обоснование

Адаптер, который сам ходит в базу за своими ключами, невозможно протестировать
на записанных фикстурах без БД, и он немедленно нарушает контракт
`carrier-isolation` в `.importlinter`.

Разделение по признаку «принадлежит тенанту / общее для платформы» совпадает
с границей применения RLS, что делает миграцию изоляции читаемой.

## Последствия

* Слой, вызывающий адаптер, обязан расшифровать учётные данные и передать их явно.
* Запись сырья вызовов (`carrier_raw_calls`) выполняется вызывающим слоем через
  обратный вызов `on_raw_call` в `carriers/http.py`.
