# ADR-0002. UUIDv7 в качестве первичных ключей

**Статус:** принято
**Дата:** 29 августа 2026

## Контекст

Нужен тип первичного ключа для всех таблиц. Кандидаты: `bigserial`, UUIDv4, UUIDv7.

## Решение

UUIDv7 (RFC 9562), генерация на стороне приложения — `aerogram.shared.ids.uuid7`.

## Обоснование

`bigserial` раскрывает клиентам объём бизнеса: по номеру отправления видно, сколько
их всего в системе. Для B2B-платформы, где тенанты могут быть конкурентами, это
нежелательно.

UUIDv4 решает эту проблему, но разрушает локальность в B-tree: каждая вставка
попадает в случайную страницу индекса. На таблице `shipment_events`, куда пишется
поток событий трекинга, это заметная деградация.

UUIDv7 несёт в старших 48 битах время в миллисекундах: вставки идут почти
последовательно, порядок ключей совпадает с хронологическим, а младшие биты
случайны — предсказать чужой идентификатор нельзя.

Побочная польза: по идентификатору строки видно, когда она создана
(`uuid7_timestamp`), что экономит время при разборе инцидентов.

## Последствия

* Ключ занимает 16 байт вместо 8. При объёмах MVP (20 000 отправлений в месяц)
  это несущественно.
* Момент создания строки выводится из идентификатора. Это не секрет и не ПДн,
  но об этом нужно помнить при выдаче идентификаторов наружу.
